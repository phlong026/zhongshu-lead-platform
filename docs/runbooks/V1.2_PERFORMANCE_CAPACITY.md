# V1.2 性能与容量验收

本 Runbook 是 H04 的执行合同。CI 只验证工具、数据合同和门禁可以运行；正式结论必须在受保护的 staging 或生产等价环境中，使用隔离的合成租户执行。禁止使用生产客户资料、真实手机号、真实证据文件或生产账号。

## 1. 验收范围

固定覆盖以下链路：

- 登录初始化；
- 待派发客资列表、候选公司；
- 人工派发及幂等并发；
- 加盟商任务列表、详情；
- 领取及积分扣减幂等并发；
- 积分流水；
- 平台经营报表；
- 退回证据上传。

正式执行必须包含 `100`、`300`、`500` 三档并发。每个场景输出请求数、错误数、错误率、吞吐量、P50、P95 和 P99；每档同时保留 PostgreSQL 连接、等待、阻塞、死锁、临时文件和块读写时间，以及目标服务 CPU、内存和 I/O 指标。

## 2. 安全与数据前提

1. 创建可重置的隔离合成租户，并在数据库备份或快照后执行。
2. 使用三个专用账号：平台运营、接收方加盟商、平台负责人。账号不得复用生产人员账号。
3. 数据集必须声明 `synthetic_data=true`，且所有业务 ID 都来自该合成租户。
4. 100/300/500 每档使用 `dispatch_cases` 中独立的待派发合成客资、`claim_cases` 中独立的待领取派发单，以及 `evidence_cases` 中完全不重叠的合成退回申请，避免前一档状态变更污染后续档位。
5. `evidence_cases` 的三档分别至少提供 100、300、500 个退回申请 ID，合计至少 900 个且档间不得重复；工具只上传固定的无客户内容 PNG 字节。
6. 每档人工派发使用该档固定的 `idempotency_key`；领取反复请求同一合成派发单。验收目标是每档只生成一个有效派发，领取只生成一笔流水。
7. 登录只在每档开始时按角色各执行一次并记录耗时，不进行密码洪泛。
8. 报告不保存响应正文、Token、Cookie、密码、手机号、客户姓名、深链或证据对象地址。
9. GitHub `staging-performance` Environment 必须把部署分支限制为受保护的 `main`，并配置固定 `V12_PERF_BASE_URL` secret；不得允许任意分支或手工地址接收 staging 凭据。
10. 未经 staging 环境保护规则审批，不得运行 GitHub `staging-performance` job。

先对 staging 数据库创建可恢复快照，再用准备脚本生成独立公司、三个专用账号、三档派发/领取数据和 900 个互不重叠的证据上传对象。脚本拒绝复用已存在的数据集 ID；需要重跑时必须先恢复快照或更换 ID，避免在已被压测改变的状态上给出失真结果。

数据库克隆创建后必须由管理员写入数据库自身的 staging 标记；生产库禁止设置此标记：

```sql
ALTER DATABASE zhongshu_staging
  SET "zhongshu.environment_classification" = 'staging-performance';
```

标记对新连接生效。准备器必须在与目标 API 相同的 POSIX 容器环境内执行，凭据文件只能写入容器内的临时目录并保持 `0600`；Windows 宿主机上的直接执行会被拒绝。数据集可以写入被 Git 忽略的 `dist/performance/`，但凭据不得复制到宿主机或提交到仓库，压测结束后立即删除：

```bash
python scripts/prepare_performance_dataset.py \
  --database-url "$DATABASE_URL" \
  --expected-database-name "zhongshu_staging" \
  --dataset-id "h04-YYYYMMDD-run1" \
  --base-url "https://staging.example.com" \
  --credentials-output "/tmp/h04-credentials.env"
```

领取场景使用临时批准基线时，必须在准备隔离数据集时同时提供阈值和 GitHub 审批链接，禁止事后手工修改数据集：

```bash
python scripts/prepare_performance_dataset.py \
  ... \
  --claim-p95-limit-ms 5000 \
  --claim-approval-reference https://github.com/OWNER/REPOSITORY/issues/NUMBER
```

准备器同时要求 `APP_ENV=staging`、实际数据库名与 `--expected-database-name` 完全一致、数据库标记为 `staging-performance`。执行环境还必须显式配置与目标 API 相同、彼此不同且不少于 32 个字符的 `FIELD_ENCRYPTION_KEY`、`PHONE_HASH_SECRET` 和 `PHONE_FINGERPRINT_SECRET`，开发默认值和隐式回退都会被拒绝。

本地预发布等价环境不需要购买或部署远程服务。当前约定由被 Git 忽略的 `dist/local-staging/staging.env` 保存本机专用环境变量，`dist/local-staging/compose.override.yml` 仅把入口绑定为 `127.0.0.1:18080`、PostgreSQL 绑定为 `127.0.0.1:55440`；这两个地址都只允许本机访问。

当前正式本地预发布容量基线使用 `WEB_CONCURRENCY=5`，每个 API worker 配置 `DATABASE_POOL_SIZE=9`、`DATABASE_MAX_OVERFLOW=9`、`SYNC_THREADPOOL_TOKENS=18`、`MAX_IN_FLIGHT_REQUESTS=18`、`IN_FLIGHT_QUEUE_TIMEOUT_SECONDS=10` 和 `DATABASE_POOL_TIMEOUT_SECONDS=30`；五进程最大数据库连接预算为 `90`。超过每进程 18 个在途请求的突发流量在获取数据库会话前异步排队，以免连接池等待线程挤占会话清理线程；排队超过 10 秒会返回带 `Retry-After` 的 `503 SERVER_BUSY`，不得无限积压。API 关闭重复的 Uvicorn access log，但保留结构化请求日志、审计日志和错误日志。scheduler 由 Compose 固定使用独立的小池 `2 + 2` 和 4 个同步线程。PostgreSQL 保持 `max_connections=100`，从而为 scheduler、压测采样、迁移和运维连接保留 10 个连接。`300` 个客户端并发不等于必须建立 `300` 个数据库连接；每进程线程数和在途请求上限都不得超过该进程的数据库连接预算，也不得通过扩大连接预算来掩盖配置不匹配。若调整 worker 数量，必须保证 `worker × (pool_size + max_overflow) <= 90` 并重新执行本门禁。实测把预算提高到 `128` 并把 PostgreSQL 提高到 `160` 会增加事务与行锁争用，因此不作为本任务的发布配置。

也可以复制并填写 `performance/v12-staging-dataset.example.json`。正式运行时不得残留 `REPLACE_WITH_` 占位符；`dispatch_cases` 和 `claim_cases` 每档必须独立，`evidence_cases` 每档数量不得小于对应并发且三档完全不重叠。凭据只通过以下环境变量提供：

数据集的 `base_url_origin` 必须与本次命令的目标 origin 完全一致；非本机目标必须使用 HTTPS。这样可避免误把受保护合成数据发送到其他主机。

```text
V12_PERF_OPERATOR_USERNAME
V12_PERF_OPERATOR_PASSWORD
V12_PERF_RECEIVER_USERNAME
V12_PERF_RECEIVER_PASSWORD
V12_PERF_OWNER_USERNAME
V12_PERF_OWNER_PASSWORD
V12_PERF_BASE_URL
DATABASE_URL
```

`DATABASE_URL` 必须指向同一 staging 环境的 PostgreSQL；SQLite 会被拒绝。

## 3. 目标基础设施指标

压测结束后再从目标 staging 的监控系统导出三档负载窗口，格式参考 `performance/v12-target-metrics.example.json`。不得用压测前准备的静态数字替代真实窗口。每档必须包含：

- `cpu_percent_max`
- `memory_percent_max`
- `io_read_bytes`
- `io_write_bytes`

顶层必须填写环境、目标 origin、导出时间、不可变 HTTPS 引用和原始导出文件 SHA-256；每档窗口必须完整覆盖报告中的该档 `started_at` 至 `completed_at`。`source` 必须填写监控系统/导出记录标识，不得保留示例占位符。

这些值必须来自目标服务/数据库基础设施，而不是压测发起机。PostgreSQL 指标由脚本直接从 `pg_stat_activity`、`pg_stat_database` 和 `pg_settings` 只读采集；报告不保存 SQL 正文或客户行。

## 4. 执行

先验证数据合同：

```bash
python scripts/performance_v12.py \
  --dataset dist/performance/dataset.json \
  --validate-config
```

执行三档正式压测：

```bash
python scripts/performance_v12.py \
  --dataset dist/performance/dataset.json \
  --base-url https://staging.example.com \
  --profiles 100,300,500 \
  --source-commit "$GITHUB_SHA" \
  --output dist/performance/v12-performance-report.json
```

脚本同时生成 Markdown 报告。此时目标监控尚未导出、签字尚未完成，工程预检只能输出 `EVIDENCE_PENDING`；它不是正式通过证据：

```bash
python scripts/check_performance_gate.py \
  --report dist/performance/v12-performance-report.json \
  --allow-pending-signoff \
  --allow-pending-infrastructure \
  --output dist/performance/v12-performance-gate.json
```

仓库的 `Main Release Verification` 仅在受信任的手工触发、选择 `performance_action=run`、`staging-performance` Environment 已批准且专用 secrets 已配置时执行真实负载。PR 和普通 push 不连接 staging。该运行使用独立 concurrency group，不会被常规 main CI 取消。

## 5. 阈值与结论

- 列表、候选、流水和报表：P95 不超过 `1500ms`；
- 详情：P95 不超过 `1000ms`；
- 领取核心事务：P95 不超过 `500ms`；
- 登录和其他写场景：P95 不超过 `1500ms`；
- 三档所有请求错误率必须为 `0`；
- PostgreSQL `deadlocks_delta` 必须为 `0`；
- 重复领取流水、积分余额差异、重复有效派发必须全部为 `0`；
- 100 和 300 档必须全部通过；
- 500 档若只超过延迟阈值，档位和顶层门禁都输出 `CAPACITY_LIMIT_REACHED`，作为明确容量上限结论；它不会被改写为 `PASS`。错误、死锁或账务差异仍直接失败。

领取 P95 超过 `500ms` 时，只有已批准的 GitHub 基线/优化任务可以临时提高该单项阈值。数据集中的 `claim_baseline` 必须同时包含：

```json
{
  "approved": true,
  "p95_limit_ms": 750,
  "approval_reference": "https://github.com/OWNER/REPOSITORY/issues/NUMBER"
}
```

不得用基线放宽其他场景、错误率、死锁或一致性门禁。

## 6. 签字与正式门禁

压测完成后导出原始目标监控文件，计算其 SHA-256，并填写 `v12-target-metrics.example.json`。技术负责人和发布负责人复核 JSON、Markdown、原始监控导出、窗口覆盖、合成租户及数据库采样。复核通过后准备独立的 signoff JSON：

- `status`: `APPROVED`
- `approved_by`: 审批责任人
- `approved_at`: 带时区时间
- `approval_reference`: GitHub Issue/Review 链接

原始 preview 报告不得手工修改。由 finalizer 只附加监控、签字和 provenance，再执行不带豁免参数的最终门禁：

```bash
python scripts/finalize_performance_report.py \
  --preview-report dist/performance/preview/v12-performance-report.json \
  --target-metrics dist/performance/v12-target-metrics.json \
  --signoff dist/performance/v12-performance-signoff.json \
  --github-run-id "$PERFORMANCE_RUN_ID" \
  --expected-source-commit "$GITHUB_SHA" \
  --output dist/performance/v12-performance-report.signed.json

python scripts/check_performance_gate.py \
  --report dist/performance/v12-performance-report.signed.json \
  --metrics-export dist/performance/v12-target-monitoring-export.bin \
  --preview-report dist/performance/preview/v12-performance-report.json \
  --expected-source-commit "$GITHUB_SHA" \
  --output dist/performance/v12-performance-gate.final.json
```

最终门禁会重新计算原始监控导出的 SHA-256，并要求它与三档报告完全一致；还会校验环境、origin、监控窗口和导出时间。GitHub 上分别配置临时 `V12_PERF_SIGNOFF_JSON`、`V12_PERF_TARGET_METRICS_JSON`，并把原始监控导出做 base64 后配置为临时 `V12_PERF_METRICS_EXPORT_BASE64`。以 `performance_action=finalize` 和原始压测 `performance_run_id` 手工执行。

finalize job 会先通过 GitHub Run 元数据确认原始压测 run 成功、来自 `main`、事件为 `workflow_dispatch`，且 `headSha` 与当前受信任的 `main` 提交完全一致；随后下载 `staging-performance-<run_id>` 原始 artifact，重算其中报告的 SHA-256，再由 `finalize_performance_report.py` 只附加监控和签字字段。最终 gate 同时读取下载的原始报告，要求 run ID、artifact 名、原始报告哈希和 `source_commit_sha` 完全匹配，因此不能复用旧提交的证据或用重写后的性能数字替换真实压测产物。该 job 不带任何 pending 豁免；成功保存 artifact 后立即删除三个临时 secret。

最终保留原始 JSON、Markdown、门禁 JSON、门禁 Markdown、目标监控导出、GitHub Run/Issue 链接和数据库快照标识。任何缺失均为 `NO-GO`。

## 7. 执行后处理

1. 保存全部证据后停止负载，不在目标环境反复重跑失败档位。
2. 执行 `python scripts/reconcile_v12.py` 并保留输出。
3. 核对派发单、领取流水和积分余额；任何差异先冻结灰度。
4. 从执行前快照恢复或清理整个合成租户，不逐条删除以免遗漏证据对象或审计记录。
5. 若 500 档为 `CAPACITY_LIMIT_REACHED`，记录瓶颈、资源水位和下一次扩容/优化任务；不得把它改写为通过。
