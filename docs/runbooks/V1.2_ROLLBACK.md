# 合家美宅客资平台 V1.2 回滚与故障恢复 Runbook

> 本 Runbook 的 `代码完成` 与 `自动化通过`只证明恢复工具和合同可执行；只有目标环境恢复演练与签字完成，才记为 `真实环境验收`。

## 1. 原则

- 先止损、后定位、再恢复；
- 不删除审计或不可变积分流水；
- 数据库变更优先通过上线前备份恢复，不盲目执行 downgrade；
- 数据库恢复成功只代表数据可读，不代表可以恢复业务流量；
- 任何回滚都必须记录触发时间、业务影响、命令、数据处理和最终验证；
- 涉及个人信息泄露时立即关闭相关入口、轮换密钥并启动合规响应。

## 2. 回滚资产

上线前必须确认：

- 上一生产版本 `APP_VERSION`；
- 上一生产版本 `镜像tag@sha256:digest`；
- V1.2 上线镜像 `tag@sha256:digest`；
- PostgreSQL 即时备份及 SHA-256；
- 对象存储上线前版本/快照；
- 对应密钥版本和恢复权限；
- `.env` 配置备份；
- 回滚执行人、审核人和通知群。

## 3. 触发条件

| 场景 | 级别 | 立即动作 |
|---|---|---|
| 迁移失败或数据校验不一致 | P0 | 停止 API/Scheduler，保持维护页，恢复备份 |
| 重复扣分、奖励或返分错误 | P0 | 关闭领取/结算/终审入口，冻结财务操作 |
| 手机号、Token、证据越权泄露 | P0 | 关闭公网入口，轮换密钥，保全日志 |
| 微信 OAuth 全面失败 | P0 | 关闭服务号菜单或切换维护页 |
| 5xx 持续超阈值、容器重启 | P0 | 停止扩量，回滚应用镜像 |
| Scheduler 停摆或严重积压 | P1 | 暂停自动任务，单独回滚 Scheduler |
| 对象存储不可用 | P1 | 暂停证据上传/读取，恢复配置或对象版本 |
| 试点关键流程阻断 | P1 | 停止新增试点，保留现有数据和审计 |

## 4. 应用回滚

应用回滚必须同时切换版本号和不可变镜像引用。例如回到 V1.0.1：

```bash
APP_VERSION=1.0.1
APP_IMAGE=registry.example.com/zhongshu-lead-platform:1.0.1@sha256:<previous-digest>
```

写入 `.env` 后执行：

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  up -d --no-deps api scheduler lead-export-worker
curl -fsS https://app.example.com/health/live
curl -fsS https://app.example.com/health/ready
```

注意：旧应用是否兼容已升级数据库必须在预演中确认。无法确认时不要只回滚应用，应进入数据库恢复流程。

## 5. 数据库恢复

1. 保持 API、Scheduler、Lead Export Worker 停止；
2. 保存故障数据库快照用于调查；
3. 校验上线前备份 SHA-256；
4. 使用恢复脚本。正式生产默认**不要**设置 `RESTORE_RESTART_SERVICES=YES`：

```bash
CONFIRM_RESTORE=YES ENV_FILE=.env \
  sh scripts/restore_postgres.sh backups/postgres/<release-backup>.dump
```

脚本无论成功或失败默认都保持 API/Scheduler 停止；失败时禁止人工绕过并直接启动应用。

5. 根据备份对应版本确认 Alembic revision；若恢复的是 V1.2 数据库：

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python -m alembic -c alembic.ini current --check-heads
```

6. 使用与备份 schema/代码匹配的 `APP_VERSION` 和不可变镜像；
7. 对 V1.2 备份执行 reconciliation，并持久化证据：

```bash
mkdir -p dist
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python scripts/reconcile_v12.py \
  > dist/v12-reconciliation-after-rollback.json
python -m json.tool dist/v12-reconciliation-after-rollback.json >/dev/null
```

若回滚到旧版数据库，则执行该旧版本对应的对账与验收，而不是强行运行 V1.2 脚本。

8. 在维护状态完成权限、积分、派发、退回和核心流程冒烟；
9. 只有 revision、对账和冒烟全部通过，才手工恢复 API/Scheduler：

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml up -d api scheduler lead-export-worker
```

禁止直接在生产执行未经预演的 `alembic downgrade`。

## 6. 账务异常

- 立即停止领取、充值、返分、奖励结算和冲正；
- 导出受影响公司、业务 ID、流水 ID 和幂等键；
- 不直接修改或删除 `points_ledgers`；
- 由财务和研发依据不可变流水制定补偿/冲正方案；
- 恢复后运行对应版本 reconciliation，差异必须为 0；
- 所有修正写审计并经双人复核。

## 7. 通知与 Scheduler

Scheduler 可单独停止：

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml stop scheduler lead-export-worker
```

修复后利用 Outbox 和奖励幂等机制恢复处理。重启前检查：

- PENDING/FAILED/DEAD 数量；
- 到期奖励积压；
- 最近成功周期时间；
- 是否存在重复结算流水；
- 失败原因是否已消除。

## 8. 对象存储恢复

- 撤销错误桶策略或访问密钥；
- 从版本控制恢复对象；
- 按数据库 `object_key` 和 SHA-256 抽查；
- 确认对象仍为私有，短时授权过期正常；
- 切换 Bucket、Endpoint 或 Region 后，旧清理任务会拒绝在新目标执行；恢复原目标后再处理；
- 回退 migration `0014` 前，必须先将 `storage_cleanup_outbox` 全部处理为 `DELETED`，否则降级会主动终止；
- 若发生公开暴露，保存访问日志并启动隐私事件处理。

## 9. 回滚后验证

- `/health/live`、`/health/ready` 正常；
- OAuth 和账号权限正常；
- 运营、电销、财务接口没有越权字段；
- 人工派发、领取、扣分和手机号解锁正常；
- 退回、核验、终审和返分正常；
- 奖励结算和冲正幂等；
- Outbox、Scheduler 和告警恢复；
- 积分与业务对账通过；
- 试点用户确认核心流程可用。
