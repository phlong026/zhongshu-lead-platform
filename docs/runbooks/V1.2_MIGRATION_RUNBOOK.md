# V1.2 数据迁移 Runbook

## 1. 迁移目标

- 从 V1.0.1 数据结构升级到 Alembic `head`；
- 为历史客资生成独立 HMAC-SHA256 手机号指纹；
- 保持历史业务状态只读，不批量改写历史事实；
- 对积分、派发、退回、奖励和证据元数据进行上线前对账。

## 2. 强制前置条件

- 生产写入已冻结；
- 最新 PostgreSQL 与对象存储备份已校验并异地保存；
- `FIELD_ENCRYPTION_KEY` 可解密历史手机号；
- `PHONE_FINGERPRINT_SECRET` 已独立生成、托管，且不会在迁移后更换；
- 同版本 PostgreSQL 全量预演已通过；
- `docker compose ... up -d db` 已启动且数据库健康；
- 回滚负责人、停止条件和恢复命令已确认。

下述生产命令统一通过 `docker-compose.yml + docker-compose.prod.yml` 的 API 一次性容器访问 `db:5432`。生产数据库不要求向宿主机暴露 5432。

## 3. V1.0.1 预升级基线

升级前只能执行不依赖 V1.2 字段和表的检查。禁止在 V1.0.1 结构上提前运行 `migrate_v12_data.py` 或 `reconcile_v12.py`，因为此时尚无 `leads.phone_fingerprint` 和 `v12_migration_checkpoints`。

```bash
mkdir -p dist
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python -m alembic -c alembic.ini current \
  > dist/v101-alembic-before.txt

docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python scripts/baseline_v101.py \
  > dist/v101-baseline-before.json
python -m json.tool dist/v101-baseline-before.json >/dev/null
```

基线报告仅统计 V1.0.1 表记录数、状态分布和积分汇总，不读取或输出手机号等个人信息。将报告、数据库大小、当前 Alembic revision 和备份校验值一并归档。

## 4. Alembic 升级

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=true api true
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python -m alembic -c alembic.ini current --check-heads
```

记录开始时间、结束时间、锁等待、数据库大小和错误输出。超过预演时长 150%、出现长时间阻塞或任一迁移异常时立即停止。

## 5. V1.2 回填只读预检

完成结构升级后，先执行只读扫描：

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python scripts/migrate_v12_data.py --dry-run \
  --batch-size 500 --max-batches 10000 --fail-on-row-error

docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python scripts/reconcile_v12.py --allow-incomplete-backfill \
  > dist/v12-reconciliation-before-backfill.json || true
python -m json.tool dist/v12-reconciliation-before-backfill.json >/dev/null
```

`reconcile_v12.py --allow-incomplete-backfill` 仅用于升级后的回填前基线；除“指纹尚未回填”之外出现未知历史状态、重复有效派发单、积分差异、缺失流水或证据异常时，不得进入正式回填。

只读扫描出现 `PHONE_DECRYPT_FAILED` 或 `PHONE_FORMAT_INVALID` 时不得继续，应先修复数据或形成有审批的排除清单。

## 6. 手机号指纹回填

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python scripts/migrate_v12_data.py \
  --batch-size 500 \
  --max-batches 10000 \
  --fail-on-row-error
```

实现特性：

- 按业务 ID 有界分页；
- 每批提交，支持断点续跑；
- 使用 `v12_migration_checkpoints` 保存游标、处理数和错误数；
- 已生成指纹的记录不会重复处理；
- 检查点只记录业务 ID 和错误码，不记录手机号；
- 失败行整改后可以显式重置检查点重新扫描。

生产重置必须由数据负责人审批并使用双重确认：

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python scripts/migrate_v12_data.py \
  --reset \
  --confirm-reset RESET_PHONE_FINGERPRINT_CHECKPOINT \
  --batch-size 500 \
  --max-batches 10000
```

`--reset` 不删除已生成指纹，只重置检查点游标、计数和错误样本。

## 7. 历史状态只读映射

V1.0.1 状态通过 `state_machine_v12.py` 映射为 V1.2 展示状态，不直接批量改写原始状态。迁移与对账使用严格模式；未知状态不会被静默归入关闭或过期，而是触发 `NO-GO`。

重点映射：

- `QUALIFIED` → `READY_DISPATCH`；
- `ASSIGNED` → `DISPATCHED`；
- `RETURN_PENDING` → `FOLLOWING`；
- `RETURNED` → `READY_DISPATCH`；
- 退回 `PENDING` → `SUBMITTED`；
- 退回 `NEED_MORE` → `NEED_MORE_EVIDENCE`。

## 8. 迁移后对账

最终报告必须写入宿主机，禁止只写到 `docker compose run --rm` 容器内部：

```bash
docker compose --env-file .env -f docker-compose.yml -f docker-compose.prod.yml \
  run --rm -T -e RUN_DB_MIGRATIONS=false api \
  python scripts/reconcile_v12.py \
  > dist/v12-reconciliation-after.json
python -m json.tool dist/v12-reconciliation-after.json >/dev/null
```

必须满足：

- 所有历史客资均有手机号指纹；
- 回填检查点为 `COMPLETED` 且错误数为 0；
- 无未知客资或退回状态；
- 同一客资最多一个有效派发单；
- 每家公司积分余额等于流水汇总和最新 `balance_after`；
- `SETTLED` 奖励均有关联流水；
- `REVERSED` 奖励均有关联反向流水；
- `APPROVED` 退回均有关联返分流水；
- 证据 `object_key`、SHA-256 和文件大小完整。

同时将 `v101-baseline-before.json` 与迁移后报告的共有指标进行比对，确认迁移未意外删除历史记录。

## 9. 最终生产 Preflight

```bash
python scripts/preflight_v12.py \
  --env-file .env \
  --require-certificates \
  --compose-database \
  --output dist/v12-preflight.json
```

`--compose-database` 强制 Alembic revision 与 V1.2 reconciliation 通过生产 Compose 网络执行。Preflight 输出不得包含数据库 URL、口令、Token 或其他敏感值。

## 10. 抽样要求

至少抽查：

- 20 条历史手机号及 90/180/365 天去重结论；
- 所有存在余额的公司，或不少于 20 家公司积分账；
- 10 条领取、10 条退回、10 条奖励；
- 截图和录音各不少于 5 个对象；
- 所有迁移错误或告警记录。

抽样表中不得记录明文手机号，应使用业务 ID 和脱敏号码。

## 11. 停止与回滚条件

立即停止：

- 基线、迁移或对账脚本非零退出；
- 数据库锁等待超过预演阈值；
- 手机号解密或指纹失败；
- 积分、奖励或返分对账出现差异；
- 证据对象大量缺失；
- 未知历史状态无法确认；
- 数据库或磁盘容量异常。

数据库恢复参见 `V1.2_ROLLBACK.md`。禁止在没有确认可逆性的情况下直接执行 Alembic downgrade。
