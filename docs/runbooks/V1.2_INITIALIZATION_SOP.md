# 合家美宅客资平台 V1.2 五角色初始化与操作 SOP

## 1. 适用范围与正式入口

本手册面向超级管理员、运营人员、电销人员、加盟商负责人和加盟商员工。当前是响应式 H5 + PC 管理台，不是原生微信小程序。以下是唯一正式入口；历史地址会重定向，不能作为验收或日常操作入口。

| 使用端 | 正式入口 | 使用人 | 说明 |
| --- | --- | --- | --- |
| 平台管理台 | `/admin/` | 未登录、`SUPER_ADMIN`、`OPERATION` | 同一登录页；登录后按角色进入统一工作台 |
| 平台响应式工作台 | `/h5/admin/` | `SUPER_ADMIN`、`OPERATION` | 独立 V1.2 移动壳；按角色呈现待办和底栏，复用同一后端权限与业务 API |
| 电销 H5 | `/h5/call/` | `TELESALES` | 仅显示运营已派发给本人的核验任务 |
| 加盟商 H5 | `/h5/` | `FRANCHISE_OWNER`、`FRANCHISE_EMPLOYEE` | 登录后进入 `/h5/v12-workbench.html` |

### 1.1 冻结项与操作纪律

- 微信 AppSecret、真实 OAuth、网页授权域名和真实客资上传当前暂缓，待具备授权的业务人员在生产控制台完成；不得在文档、截图或日志中抄录密钥。
- 配置参数、积分档位、价格规则和正式工作日历只有经过业务批准才能变更；未批准时不得执行变更，且判定为 `NO-GO`。
- 所有数据库迁移、备份与回滚按 `docs/runbooks/DEPLOYMENT.md`、`docs/runbooks/V1.2_MIGRATION_RUNBOOK.md` 和 `docs/runbooks/V1.2_ROLLBACK.md` 执行。
- 本地自动化通过只证明候选代码可运行；真实环境验收中的微信、生产数据、灾备、移动端和业务 UAT 必须分别留证。

## 2. 固定五角色与职责边界

权限基线是 `apps/api/src/services/rbac.py`，账号迁移基线是 `apps/api/src/core/role_contract.py`。每个账号只能拥有一个有效业务角色。

| 角色 | 主要职责 | 明确不能做的事 |
| --- | --- | --- |
| `SUPER_ADMIN` | 全部权限；开通/停用平台账号、发起加盟商负责人微信绑定；积分充值、冲正、审计和应急治理 | 不得删除审计或积分流水；代为操作加盟商账号时必须填写理由 |
| `OPERATION` | 初审、加盟商能力/区域审核、派发、前置电销任务派发、退回终审及后续处置；客资总览查看当前加盟商跟进人 | 不得充值或冲正积分；不查看加盟商员工之间的分配/回收历史 |
| `TELESALES` | 处理运营派发的前置核验和退回核验，记录拨号和事实结论 | 不得自主领取、转派任务；不得决定派发、退款、关闭或退回加盟商 |
| `FRANCHISE_OWNER` | 管理本公司资料/能力/区域；提交或领取客资；公司内部把已领取客资分配给本公司员工 | 不得查看其他公司数据；不得修改平台审核、积分或审计 |
| `FRANCHISE_EMPLOYEE` | 提交本人客资；处理负责人明确分给自己的已领取客资、跟进和退回材料 | 不得查看公司其他员工的个人任务；不得管理公司账号、能力或区域 |

加盟商能否供客/接客由 `LEAD_SUPPLIER`、`LEAD_RECEIVER` 能力和服务区域决定，不额外创建“供应商”角色。

## 3. 管理员首装与初始化 SOP

### 3.1 前提

- 确认当前 Git 提交、数据库备份和 Alembic revision；生产窗口内先完成写入冻结。
- 在备份前先导出迁移核对快照；快照只包含账号角色、公司、能力区域、积分、在途业务和奖励的关联字段，不含密码、令牌、完整手机号或原始客资。输出文件为内部资料，默认权限为 `0600`，不得上传到代码仓库：

  ```bash
  mkdir -p dist
  python scripts/export_five_role_migration_snapshot.py \
    --output "dist/five-role-migration-snapshot-$(date +%Y%m%d-%H%M%S).json"
  ```

- 先执行 `python scripts/sync_rbac.py` 预览，再经复核执行 `python scripts/sync_rbac.py --apply --source release_v1.2.5`。
- 若存在历史账号，先执行 `python scripts/migrate_five_role_accounts.py --dry-run`；结果无歧义后才可 `--apply`。混合角色或历史角色账号必须先人工处置，不能绕过迁移门槛登录。

### 3.2 首装步骤

| 步骤 | 入口 | 所需角色 | 操作步骤 | 成功结果 | 常见错误 | 回退方式 |
| --- | --- | --- | --- | --- | --- | --- |
| 1. 数据库迁移 | 终端 | 运维数据库权限 | 按迁移 Runbook 执行 `alembic upgrade head`，并检查 heads 和 V1.2 对账 | 数据库到当前 revision；无积分或状态不一致 | 迁移阻塞、对账异常 | 停止发布，按备份和 Rollback Runbook 恢复 |
| 2. 同步 RBAC | 终端 | 数据库运行权限 | 预览、复核 `removed`、显式应用、再次预览 | `result.changed=false`；产生 `SYSTEM_RBAC_SYNC` 审计 | 权限漂移 | 回到批准矩阵重新同步；不得手改关联表 |
| 3. 创建首位超级管理员 | 终端 | 首装权限 | `python scripts/bootstrap_superadmin.py --username <账号> --display-name <名称>` | `SYSTEM_SUPERADMIN_BOOTSTRAP` 审计存在，密码不写审计 | 密码不符合策略、数据库状态异常、`LAST_SUPER_ADMIN_REQUIRED` | 先建立第二名超级管理员后再停用错误账号 |
| 4. 平台首次登录 | `/admin/` | `SUPER_ADMIN` | 输入内部账号，确认进入 `/admin/v12-operations.html` | 左侧显示身份和菜单；右上只显示刷新、设置、退出 | 会话失效、账号停用 | 核对状态和服务日志；不要创建重复账号 |
| 5. 建立运营与电销账号 | 平台工作台“设置” | `SUPER_ADMIN` | 新建 `OPERATION`、`TELESALES` 或额外 `SUPER_ADMIN`；记录一次性初始密码 | 每人只一个业务角色，旧会话会因重置失效 | `AUTH_ROLE_MIGRATION_REQUIRED`、账号重复 | 重置密码或停用错误账号；不得赋予历史角色 |
| 6. 创建加盟商公司 | 平台工作台“加盟商” | `SUPER_ADMIN` | 建立公司、负责人、主要服务城市和区县 | 公司和积分账户就绪，能力/区域待审核 | `REGION_NOT_FOUND`、层级错误 | 在审核前修正；停止合作时停用公司，不删除历史 |
| 7. 绑定加盟商负责人 | “加盟商 → 发起负责人绑定” | `OPERATION` 或 `SUPER_ADMIN` | 生成一次性邀请，由负责人在未登录平台账号的微信内打开并确认 OAuth | 微信自动建立 `FRANCHISE_OWNER` 账号并绑定目标加盟商；不输入账号密码 | `AUTH_BINDING_REQUIRES_CLEAN_SESSION`、`AUTH_COMPANY_ALREADY_BOUND` | 先退出已登录平台账号；如需换人，先解绑原负责人微信后重新发邀请 |
| 8. 审核能力与区域 | “加盟商” | `OPERATION` 或 `SUPER_ADMIN` | 审核供客/接客能力和服务区域；可一并核对公司资料 | 通过状态可追溯，接收资格即时生效 | 能力/区域不存在、驳回理由为空 | 加盟商修正后重新申请，禁止改库 |
| 9. 积分充值 | “资金” | `SUPER_ADMIN` | 选择已发布档位，填写线下收款凭据，勾选已核实并提交 | 产生不可变流水、消息和审计 | `POINTS_RECHARGE_CONFIRM_REQUIRED`、档位无效 | 使用反向流水冲正；不得编辑历史记录 |
| 10. 首装验收 | 第 6 节 | 各角色代表 | 每个角色登录并验证允许与拒绝的入口 | 五角色、三端入口和关键拒绝路径均有脱敏证据 | 用超级管理员代替岗位验收 | 按真实角色重做，保留失败证据 |

## 4. 正常业务主链路

### 4.1 加盟商供客 → 初审 → 派发

1. `FRANCHISE_OWNER` 或 `FRANCHISE_EMPLOYEE` 在“客资”提交客资；员工只能查看自己的供客记录。
2. `OPERATION` 在“客资”完成初审：资料完整且合格则进入 `READY_DISPATCH`；资料不足则填写派发原因并派给指定 `TELESALES`，客资进入 `PENDING_TELESALES_VERIFY`。
3. `TELESALES` 只能在 `/h5/call/` 开始本人已派发的任务，开始后查看号码、主动点击拨号、填写事实结论。
4. 电销以 `IN_PROGRESS` 完成事实核验并提交 `SUBMITTED` 结论后，客资进入 `PENDING_OPERATION_DISPOSITION`；`OPERATION` 必须填写处置说明，决定进入派发池、退回补充、标记重复或关闭。
5. `OPERATION` 在“派发”选择符合公司状态、能力、区域和积分条件的加盟商。系统生成派发单、事件和积分链路。
6. 加盟商负责人在本公司内分配已领取客资给员工；这不是运营审批事项。运营可在客资总览查看当前跟进人，但不能查看员工之间的分配/回收历史。

### 4.2 领取 → 跟进 → 退回 → 核验 → 终审

1. 加盟商负责人领取本公司派发单，系统记录扣分和领取事件；负责人可在公司内部交给员工处理。
2. 负责人或被分配员工填写跟进。每条跟进与业务对象和操作人可追溯。
3. 不合格客资在规则期限内发起退回，上传截图或录音等材料后提交。
4. `OPERATION` 在“异常”把退回核验派给指定电销，派发/改派必须填理由；审计同时保留原责任人、当前责任人与理由。
5. `TELESALES` 只核实事实并提交 `SUPPORT_RETURN`、`DOES_NOT_SUPPORT_RETURN` 或 `INCONCLUSIVE`，不决定退款或退回加盟商。
6. `OPERATION` 查看材料和电销事实结论，完成终审；系统按结果冻结、返还或保留积分，并保留不可变流水。

### 4.3 可追溯性检查

对任一客资、派发单或退回编号，在“审计”输入业务编号并打开“完整业务记录”。验收时应能看到：提交、初审、前置核验、派发、领取、内部公司协作、跟进、退回、电话核验、终审、积分、通知和操作人时间线。

## 5. 各角色日常操作要点

### 超级管理员

- 加盟商账号开通、停用和密码重置与运营拥有同样的执行能力，但界面会强制填写理由；审计中不记录密码。
- 充值无需第二名超级管理员复核，但必须核实线下款项、外部凭据和一次性幂等键。
- 正常账号只用停用、重置和解绑处理；仅已停用、已标记且无业务数据的内部测试账号可以在完整账号和原因二次确认后删除；审计和积分流水永不随账号删除。

### 运营人员

- 首页优先处理初审、待电销派发、待电销结论、待派发和待退回终审。
- “加盟商”页只能处理公司状态、账号、能力和区域；当前跟进人只在客资总览展示，不在加盟商页开放员工任务或交接历史。
- 电销结论是事实输入，不是业务决定。所有后续派发、补充、重复、关闭和终审由运营明确提交。

### 电销人员

- “首页”显示待办；“核验”只显示本人 `ASSIGNED`、`IN_PROGRESS` 任务；“记录”显示已提交事实结论。
- 无任务时显示空状态，不存在抢单、领取、改派、派发、退款或积分入口。
- 号码只能在开始本人任务后读取，拨号必须由本人点击，拨号事件写审计。

### 加盟商负责人和员工

- 负责人管理公司资料、能力、区域和内部员工协作；员工不具备这些入口。
- 两者可按授权提交客资；员工只能查看自己提交的客资和负责人分配给自己的接收客资。
- 退回材料必须真实；电销、运营和超级管理员都可在业务链路中追溯材料和结论。

## 6. 上线前强制门槛

以下六项是页面开发完成和生产切换的共同 `GO` 门槛；任一项失败即 `NO-GO`：

1. 固定五角色、单角色登录、账号生命周期和数据范围已验收。
2. 客资、前置核验、派发、领取、退回和终审状态机均有正向和越权/非法状态负向测试。
3. 加盟商内部协作历史严格公司内可见；运营与超级管理员仅在客资总览查看当前跟进人，超级管理员查询交接历史仍必须有理由与审计。
4. 积分充值、扣减、冻结、返还和冲正能从业务对象追溯到不可变流水并完成对账。
5. `/admin/`、`/h5/admin/`、`/h5/call/`、`/h5/` 均经响应式浏览器 smoke 验收；历史页面仅重定向，不再承担业务写入。
6. 迁移、RBAC 同步、健康检查、备份恢复演练、对象存储、真实微信外部回调和业务 UAT 分别留有证据；本地测试不能替代生产验收。
