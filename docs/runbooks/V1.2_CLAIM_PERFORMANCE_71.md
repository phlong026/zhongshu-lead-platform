# V1.2 Issue #71 Claim 性能优化与本地 Release Gate

## 1. 目标

Issue #71 只优化 Claim 高并发路径，不以降低积分、归属、幂等、审计或状态机正确性换取性能。

必须分别验证：

1. `replay`：同一个 Assignment 被大量重复 Claim；
2. `distributed`：多个加盟商同时 Claim 不同 Assignment；
3. `hot_account`：同一加盟商同时 Claim 多个不同 Assignment。

固定结论规则：

- replay / distributed 的 100、300 档：P95 ≤ 500ms 为硬门禁；
- 500 档超过 500ms 可记为 `CAPACITY_LIMIT_REACHED`，但错误、死锁或账务差异仍是失败；
- hot-account 重点确定单积分账户强一致写入容量，不允许为了 500ms 取消 PointsAccount 串行化；
- 所有场景要求 HTTP 业务错误率 0、`duplicate_claim_ledgers=0`、`points_balance_mismatches=0`、`duplicate_active_assignments=0`、deadlock delta=0。

## 8. 执行 100/300/500 Claim Gate

先固定本地精确 SHA：

```bash
CANDIDATE_SHA="$(git rev-parse HEAD)"
```

执行全部三类场景：

```bash
python scripts/claim_performance_v12.py \
  --dataset /tmp/p71-claim-dataset.json \
  --database-url "$DATABASE_URL" \
  --source-commit "$CANDIDATE_SHA" \
  --scenarios replay distributed hot_account \
  --profiles 100 300 500 \
  --output dist/performance/p71-claim-performance.json
```

脚本会：

- 输出 P50/P95/P99、throughput、error rate；
- 每 50ms 只读采集 PostgreSQL connections / wait / lock wait / blocked / slow query / deadlock；
- 每档前后执行一致性快照；
- replay 强制恰好 1 个首次 Claim，其余全部 idempotent；
- distributed/hot-account 强制每个 Assignment 都是首次 Claim；
- `data.idempotent` 必须是 JSON boolean；
- company mismatch、HTTP failure、错误的 first-claim/replay 数量、deadlock 或一致性差异全部 fail-closed；
- 报告绑定 `source_commit`；
- 100/300 replay + distributed 超过 500ms 会使 CLI 返回非 0；
- 500 超时延但无正确性问题只记录 `CAPACITY_LIMIT_REACHED`；
- hot-account 记录真实容量，不通过削弱账务语义换延迟。

## 9. Replay 特别验收

每档必须：

- `first_claims=1`；
- `idempotent_replays=profile-1`；
- 一条 Claim PointsLedger；
- 一个 `V12_CLAIMED` AssignmentEvent；
- 一个 `V12_ASSIGNMENT_CLAIM` 业务 Audit；
- 无重复通知业务事实。

300 档核心门禁：P95 ≤ 500ms。

## 10. Distributed 特别验收

数据集至少使用 2 个不同 receiver company；默认准备器创建 20 家。每条响应必须回到其预期 company，300 档 P95 ≤ 500ms。

如失败，先看：API in-flight / threadpool、DB peak connections、PointsAccount 热点分布、lock wait、slow query、CPU/内存/I/O，不得直接扩 PostgreSQL 连接预算掩盖问题。

## 11. Hot Account 特别验收

同一 company 对不同 Assignment 并发扣积分。首要门禁：

- 0 负余额；
- 0 duplicate Claim ledger；
- PointsAccount 与 PointsLedger 对账一致；
- 0 deadlock；
- 0 duplicate active assignment。

如果 Hot Account 300 档高于 500ms，应形成单账户容量 SLO；现实业务不应为了极端单钱包写热点取消强一致性。

## 12. 生产等价监控与安全

同时按 H04 原 Runbook 保留目标主机/容器 CPU、内存、I/O 导出。Claim 专项报告的 DB 采样不能替代基础设施监控。

压测后至少执行：PointsAccount vs Ledger reconciliation、Assignment/Lead 状态对账、SupplierReward snapshot、Audit/Notification 去重、PII/log 泄漏检查、security negative tests、Semgrep/Trivy/SBOM/Security Gate。

任何积分差异、重复业务流水、越权、PII 泄漏或 deadlock 都是 NO-GO。

## 13. 本地 Code Review

必须检查：

- SingleFlight leader/follower 生命周期、跨 tenant key 隔离；
- leader AppError / transient error / timeout 行为；
- PostgreSQL advisory transaction lock 与 READ COMMITTED follower 可见性；
- PointsAccount 串行化与 claim 幂等；
- Assignment + Lead 状态原子性；
- 首次 Audit/Notification 和 replay 零重复业务事实；
- 工作日日历、奖励规则、手机号解锁；
- 证据是否绑定精确 Candidate SHA。

P0/P1/P2 未清零不得合并。
