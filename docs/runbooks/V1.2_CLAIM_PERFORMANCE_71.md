# V1.2 Issue #71 Claim 性能优化与本地 Release Gate

## 1. 目标与场景

Issue #71 只优化 Claim 高并发路径，不以降低积分、归属、幂等、审计或状态机正确性换取性能。

必须分别验证：

1. `replay`：同一个 Assignment 被大量重复 Claim；
2. `distributed`：多个加盟商同时 Claim 不同 Assignment；
3. `hot_account`：同一加盟商同时 Claim 多个不同 Assignment。

目标：

- `replay / 300`：P95 ≤ 500ms；
- `distributed / 300`：目标 P95 ≤ 500ms；
- `hot_account`：优先保证 0 超扣、0 重复流水、0 死锁，形成真实容量结论，不通过放松账务一致性强行满足 500ms；
- 所有场景必须 HTTP 业务错误率 0、`duplicate_claim_ledgers=0`、`points_balance_mismatches=0`、`duplicate_active_assignments=0`、deadlock delta=0。

## 7. Claim benchmark 数据合同

`scripts/claim_performance_v12.py` 的每个 case 必须提供：

```json
{
  "assignment_id": "<synthetic-assignment-id>",
  "company_id": "<receiver-company-id>",
  "credential_env_prefix": "V12_PERF_RECEIVER"
}
```

脚本会用 `company_id` 校验实际响应中的 Assignment 归属，不能仅通过不同账号前缀伪装不同积分账户。

凭据仅通过环境变量注入：

```bash
export V12_PERF_RECEIVER_USERNAME='...'
export V12_PERF_RECEIVER_PASSWORD='...'
```

脚本会 fail-closed 校验场景语义：

- replay：必须恰好 1 个首次 Claim，其余全部 idempotent replay；
- distributed/hot-account：必须每个 Assignment 都是首次 Claim，不允许预先已领取的数据伪装写负载；
- HTTP failure、company mismatch、首次 Claim/replay 数量异常均使 `scenario_valid=false`，CLI 返回非 0。

## 8. Replay Storm 100/300/500

现有 H04 每个 profile 的单一 Claim Assignment 可直接映射为 replay 数据：

```json
{
  "synthetic_data": true,
  "environment": "staging-equivalent",
  "base_url_origin": "http://127.0.0.1:18080",
  "scenarios": {
    "replay": {
      "100": [{"assignment_id": "<a100>", "company_id": "<company>", "credential_env_prefix": "V12_PERF_RECEIVER"}],
      "300": [{"assignment_id": "<a300>", "company_id": "<company>", "credential_env_prefix": "V12_PERF_RECEIVER"}],
      "500": [{"assignment_id": "<a500>", "company_id": "<company>", "credential_env_prefix": "V12_PERF_RECEIVER"}]
    }
  }
}
```

执行：

```bash
python scripts/claim_performance_v12.py \
  --dataset /tmp/claim-performance-replay.json \
  --scenarios replay \
  --profiles 100 300 500 \
  --output dist/performance/claim-replay.json
```

重点：

- 300 P95 ≤ 500ms；
- `first_claims=1`；
- `idempotent_replays=profile-1`；
- 只有 1 条 Claim PointsLedger；
- 只有 1 个 `V12_CLAIMED` Event；
- 只有 1 个 `V12_ASSIGNMENT_CLAIM` 业务 Audit；
- 无重复通知业务事实。

## 9. Distributed Claim 100/300/500

每个 profile：

- 至少 profile 个不同 Assignment；
- 至少 2 个不同 receiver `company_id`；
- 建议 10–30 个加盟商分散承担 300/500 个 Claim；
- 每个 case 的 credential 必须实际属于对应 `company_id`；
- 每家公司积分余额足够并有安全余量；
- 全部为 synthetic staging 数据。

```bash
python scripts/claim_performance_v12.py \
  --dataset /tmp/claim-performance-distributed.json \
  --scenarios distributed \
  --profiles 100 300 500 \
  --output dist/performance/claim-distributed.json
```

300 并发以 P95 ≤ 500ms 为优化目标；未达到时继续依据 DB wait、CPU、连接池和热点分布定位，不得降低账务门禁。

## 10. Hot Account 100/300/500

每个 profile：

- Assignment 必须全部不同；
- 全部 case 使用同一个 receiver `company_id`；
- 该公司的积分余额必须足够；
- credential 必须属于该 company。

```bash
python scripts/claim_performance_v12.py \
  --dataset /tmp/claim-performance-hot-account.json \
  --scenarios hot_account \
  --profiles 100 300 500 \
  --output dist/performance/claim-hot-account.json
```

Hot Account 首要门禁：0 负余额、0 重复 Claim ledger、ledger sequence/balance_after 对账正确、0 deadlock、0 duplicate active assignment。若 300 个不同扣款无法在 500ms 内完成，应形成真实单账户容量 SLO，而不是取消 PointsAccount 串行化。

## 11. 最终对账与安全复核

- PointsAccount vs PointsLedger；

任何积分差异、重复业务流水、越权、PII 泄漏或 deadlock 都是 NO-GO。
