# V1.2 Issue #71 Claim 性能优化与本地 Release Gate

## 1. 目标

Issue #71 只优化 Claim 高并发路径，不以降低积分、归属、幂等、审计或状态机正确性换取性能。

必须区分三种负载：

1. `replay`：同一个 Assignment 被大量重复 Claim，请求合并/幂等惊群场景；
2. `distributed`：多个加盟商同时 Claim 不同 Assignment，模拟真实平台并发；
3. `hot_account`：同一加盟商同时 Claim 多个不同 Assignment，测试单积分账户的强一致写入上限。

目标门禁：

- `replay / 300`：P95 ≤ 500ms；
- `distributed / 300`：目标 P95 ≤ 500ms；
- `hot_account`：必须 0 超扣、0 重复流水、0 死锁，性能形成容量结论，不通过放松账务一致性强行满足 500ms；
- 所有场景：HTTP 业务错误率 0、`duplicate_claim_ledgers=0`、`points_balance_mismatches=0`、`duplicate_active_assignments=0`、deadlock delta=0。

## 7. 第四层：Replay Storm 100/300/500

现有 H04 dataset 每个 profile 只有一个 Claim Assignment，正好用于 replay storm。

使用 `scripts/claim_performance_v12.py` 的 replay 场景时，数据合同示例：

```json
{
  "synthetic_data": true,
  "environment": "staging-equivalent",
  "base_url_origin": "http://127.0.0.1:18080",
  "scenarios": {
    "replay": {
      "100": [{"assignment_id": "<assignment-100>", "credential_env_prefix": "V12_PERF_RECEIVER"}],
      "300": [{"assignment_id": "<assignment-300>", "credential_env_prefix": "V12_PERF_RECEIVER"}],
      "500": [{"assignment_id": "<assignment-500>", "credential_env_prefix": "V12_PERF_RECEIVER"}]
    }
  }
}
```

凭据通过环境变量注入：

```bash
export V12_PERF_RECEIVER_USERNAME='...'
export V12_PERF_RECEIVER_PASSWORD='...'
```

执行：

```bash
python scripts/claim_performance_v12.py \
  --dataset /tmp/claim-performance-replay.json \
  --scenarios replay \
  --profiles 100 300 500 \
  --output dist/performance/claim-replay.json
```

验收重点：

- 300 P95 ≤ 500ms；
- 每个 profile `first_claims=1`；
- 其余成功请求为 idempotent replay；
- 只有一条 Claim PointsLedger；
- 只有一个 V12_CLAIMED AssignmentEvent；
- 只有一个 V12_ASSIGNMENT_CLAIM 业务 Audit；
- 不产生重复通知业务事实。

## 8. 第五层：Distributed Claim 100/300/500

数据要求：

- 每个 profile 至少 profile 个**不同 Assignment**；
- 至少 2 个 receiver credential prefix；
- 建议 10–30 个加盟商分散承担 300/500 条 Assignment；
- 每个公司积分余额应覆盖本 profile 的全部扣分并保留安全余量；
- 所有数据必须 synthetic、staging-only。

执行：

```bash
python scripts/claim_performance_v12.py \
  --dataset /tmp/claim-performance-distributed.json \
  --scenarios distributed \
  --profiles 100 300 500 \
  --output dist/performance/claim-distributed.json
```

300 并发以 P95 ≤ 500ms 为优化目标；如未达到，不得放宽账务门禁，必须继续依据 DB wait/CPU/连接池/热点分布定位。

## 9. 第六层：Hot Account 100/300/500

数据要求：

- 每个 profile 使用不同 Assignment；
- 同一 profile 全部由同一 receiver credential prefix 发起；
- 该公司的积分余额必须足够。

执行：

```bash
python scripts/claim_performance_v12.py \
  --dataset /tmp/claim-performance-hot-account.json \
  --scenarios hot_account \
  --profiles 100 300 500 \
  --output dist/performance/claim-hot-account.json
```

Hot Account 的首要验收是财务正确性：

- 0 负余额；
- 0 重复 Claim ledger；
- ledger sequence/balance_after 对账正确；
- 0 deadlock；
- 0 duplicate active assignment。

如果单账户 300 个不同扣款的 P95 高于 500ms，应形成真实容量上限/SLO，而不是取消 PointsAccount 串行化边界。

## 10. 第七层：最终对账与安全复核

压测结束后至少执行：

- PointsAccount vs PointsLedger reconciliation；
- assignment/lead current state reconciliation；
- supplier reward 数量与快照检查；
- Audit/Notification 去重检查；
- PII/log 泄漏检查；
- security negative tests；
- Semgrep/Trivy/SBOM/Security Gate。

任何积分差异、重复业务流水、越权、PII 泄漏或 deadlock 都是 NO-GO。
