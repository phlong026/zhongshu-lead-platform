## 3. 必须重建 Candidate staging 镜像

Dockerfile 会把 Git revision 烘焙进 `/app/.build-sha`，`/health/ready` 会返回 `build_sha`。最终 runner 会先比较目标 API 的 `build_sha` 与 `CANDIDATE_SHA`，不一致直接拒绝压测，避免“测试 A 提交、部署 B 提交”。

## 6. 最终 Candidate-bound Claim Gate

**最终只能运行这个入口：**

```bash
python scripts/claim_release_gate_v12.py \
  --dataset /tmp/p71-claim-dataset.json \
  --database-url "$DATABASE_URL" \
  --source-commit "$CANDIDATE_SHA" \
  --scenarios replay distributed hot_account \
  --profiles 100 300 500 \
  --output dist/performance/p71-claim-release-evidence.json
```

该入口在发起负载前会同时验证：

1. 本地 Git HEAD = `source_commit`；
2. 目标 API `/health/ready.build_sha` = `source_commit`；
3. Claim Assignment 为全新 PENDING 数据；
4. Claim Ledger/Event/Audit 还不存在；
5. Claim Notification/Outbox 还不存在。

压测过程中：

- 50ms PostgreSQL sampler 必须先完成 baseline handshake，再启动请求计时；
- replay / distributed / hot-account 分开统计；
- 100/300 replay + distributed 固定 P95 ≤ 500ms；
- 500 超过 500ms 可标记 `CAPACITY_LIMIT_REACHED`，但正确性门禁不放宽；
- hot-account 形成单钱包强一致容量结论，不以削弱积分串行化换性能。

压测后会 fail-closed 验证：

- Assignment.company_id / receiver_company_id 与 case 绑定一致；
- Assignment/Lead 状态与 current_assignment_id 一致；
- 每个 Assignment 恰好 1 条、且属于预期 company 的 `V12_ASSIGNMENT_CLAIM` Claim PointsLedger；
- 每个 Assignment 恰好 1 个 `V12_CLAIMED` Event；
- 每个 Assignment 恰好 1 条、且 company/resource 绑定正确的 `V12_ASSIGNMENT_CLAIM` Audit；
- 每个 Assignment 恰好 1 条 receiver Claim Notification；
- 每个 Assignment 恰好 1 条 company/business_id 绑定正确的 Claim NotificationOutbox；
- deadlock delta = 0；
- duplicate claim ledger = 0；
- points balance mismatch = 0；
- duplicate active assignment = 0。

任何一项失败，最终 CLI 返回非 0。
