# 42 - V1.2 Sprint 1 客资供给后端评审

- 分支：`feature/v1.2-sprint1-lead-supply-backend`
- 目标分支：`release/v1.2.0`
- 评审范围：T04、T06-T10、T12-T13 后端实现
- 不在本 PR：T05 管理后台录入页面、T11 供应商 H5 页面
- 结论：通过

## 1. 已实现能力

1. 平台客资草稿创建、编辑、提交、列表。
2. 供应商客资草稿创建、编辑、提交、公司级列表与详情隔离。
3. 供应商上传能力申请/审核，以及 `LEAD_SUPPLIER` 生效校验。
4. 公司服务区域申请、平台审核、主要城市与多区域配置。
5. 手机号规范化、密文存储和独立 HMAC-SHA256 指纹。
6. 90/180/365 天三段去重结论、去重事件、历史兼容关系和人工覆盖。
7. 平台手工录入校验通过后直接进入 `READY_DISPATCH`，不创建前置电销任务。
8. 供应商客资提交后进入 `PENDING_REVIEW`，资料初审通过且复检通过后直接进入 `READY_DISPATCH`。
9. 新增角色/权限、对象级归属校验、高风险审计和敏感字段脱敏。

## 2. 关键业务规则复核

- [x] 平台手工录入不经过前置电销。
- [x] 供应商必须具备已审核、已启用的 `LEAD_SUPPLIER` 能力。
- [x] 已批准但停用的公司能力可以重新发起审核，不会形成无法恢复的死状态。
- [x] 供应商只能访问本公司客资。
- [x] 草稿不参与其他客资的重复命中，避免未提交数据阻断正式客资。
- [x] 90 天内为硬重复，91-180 天为奖励重复，181-365 天为历史疑似。
- [x] 奖励重复不阻断派发，但保留奖励资格结论供后续奖励服务使用。
- [x] 历史疑似进入人工复核，不直接进入待派发池。
- [x] 人工覆盖必须关联当前客资的可复核去重事件、填写至少 5 个字符原因并保留审计。
- [x] 正常 `CLEAR` 结论不得人工伪造覆盖。
- [x] 服务区域必须包含一个城市级主要城市，其他区域必须为其下属区县。
- [x] 服务区域新增/恢复必须审核后生效；已批准区域的移除在平台审核前继续有效。

## 3. 安全与权限评审

- 手机号正文仅以加密字段存储，去重使用 HMAC 指纹。
- 审计服务递归屏蔽手机号、密文、哈希、指纹、密码、令牌和密钥；仅保留脱敏手机号。
- 平台录入草稿默认仅提交人可修改；超级管理员可覆盖。
- 供应商接口同时校验权限、公司有效状态、公司能力和对象公司归属。
- 供应商资料初审、去重覆盖、公司能力审核和服务区域审核均为独立权限。
- 去重覆盖权限标记为敏感权限。

## 4. 评审发现与修复

### F-01 版本测试硬编码

- 现象：V1.0.1 生产就绪测试写死 `1.0.1`，V1.2 健康检查正确返回 `1.2.0` 后导致 CI 失败。
- 修复：测试改为校验健康检查版本与应用元数据一致。
- 状态：已关闭。

### F-02 审计接口与敏感字段

- 现象：新增路由传入 `reason`，旧审计函数不接受；客资快照中也可能带明文手机号。
- 修复：审计函数正式支持原因元数据，并在写库前递归脱敏。
- 状态：已关闭。

### F-03 草稿误命中重复

- 现象：已保存但未提交的草稿可能阻断后续正式提交。
- 修复：去重候选明确排除 `DRAFT`。
- 状态：已关闭。

### F-04 正常客资可被错误覆盖

- 现象：人工覆盖服务缺少有效重复状态守卫。
- 修复：仅 `HARD_DUPLICATE`、`REWARD_DUPLICATE`、`HISTORICAL_SUSPECT` 可覆盖，且事件必须属于当前客资。
- 状态：已关闭。

### F-05 服务区域修改中断已批准覆盖

- 现象：简单替换会在平台审核前删除原有有效服务区域。
- 修复：新增/恢复区域待审核且暂不生效；移除申请在审核前继续保持有效，批准后才停用。
- 状态：已关闭。

### F-06 停用能力无法重新申请

- 现象：能力记录处于 `APPROVED + inactive` 时，原申请逻辑不会重新进入待审核。
- 修复：非“已批准且启用”的能力再次申请时统一转为 `PENDING + inactive`。
- 状态：已关闭。

### F-07 服务区域层级缺少硬约束

- 现象：区县可被错误选择为主要城市，也可提交不属于主要城市的区县。
- 修复：主要城市字段改为必填并必须为 `CITY`；其他区域必须为其直接下属 `DISTRICT`。
- 状态：已关闭。
