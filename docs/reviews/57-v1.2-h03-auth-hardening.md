## 问题基线

内部管理账号已经使用 Argon2 + JWT + HttpOnly Cookie，但上线前评审确认仍存在以下生产风险：

1. `/api/v1/auth/login` 只有通用 API 级限流，缺少登录专项来源 IP 防护；
2. 内部账号没有持久化失败次数和临时锁定；
3. 登录失败、锁定、恢复缺少集中安全审计；
4. 浏览器登录 JSON 暴露 raw JWT；
5. WAF/VPN/LB 场景的真实客户端 IP 信任边界不明确；
6. SQLite 默认开发/测试数据库对 `FOR UPDATE` 无效；
7. 新认证模型若未进入 Alembic metadata，未来 autogenerate 存在误删表风险。

## 最终实现

### 账号级锁定

新增独立 `auth_login_state` 表，一对一保存 `failed_count / last_failed_at / locked_until`。默认 15 分钟失败窗口内累计 5 次失败后锁定 15 分钟。

- PostgreSQL：同账号认证先锁 User 行，串行化同账号并发尝试；
- SQLite：错误计数使用单条 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` 原子 UPSERT；
- 锁定期正确密码不能绕过；
- 锁定到期后自动恢复并写 `AUTH_LOGIN_UNLOCKED`；
- 安全状态在错误响应前显式提交，失败请求不会回滚锁定事实。

### 防账号枚举

内部账号的以下失败场景对外统一为：

- HTTP `401`
- code `AUTH_LOGIN_FAILED`
- message `用户名或密码错误`

覆盖：未知用户名、错误密码、已锁定账号、已停用账号。

服务端仍通过审计动作区分 `AUTH_LOGIN_FAILED / AUTH_LOGIN_LOCKED / AUTH_LOGIN_BLOCKED`，既保留安全运营能力，又不向匿名调用方泄露账号存在性、锁定或停用状态。

未知用户名继续执行 Argon2 dummy verify，使计算路径更接近真实密码校验。

### IP 级登录限流

Nginx 为 `/api/v1/auth/login` 建立独立 `auth_login_limit`：`10r/m`、`burst=5`，边缘层超限返回 429。

真实 IP 只从显式 `TRUSTED_PROXY_CIDR` 恢复：

- `set_real_ip_from ${TRUSTED_PROXY_CIDR}`；
- `real_ip_header X-Forwarded-For`；
- `real_ip_recursive on`。

生产配置通过 Python `ipaddress.ip_network` 强校验，只允许单一、规范、非 `/0` 的 CIDR；拒绝空值、非 CIDR、尾随 token、额外 Nginx 指令、非 canonical network。默认 Compose 只信任 `127.0.0.1/32`，实际 WAF/VPN/LB 必须配置其精确可信出口网段。

### Cookie-only 浏览器会话

内部 `/auth/login` 成功后 JWT 只写 `access_token` Cookie：

- HttpOnly；
- production Secure；
- SameSite=Lax；
- Path=/。

登录 JSON 只返回 user 摘要，不返回 raw JWT。测试需要多角色 Bearer 时，从 TestClient 的 Set-Cookie 读取 token，不新增生产 token endpoint。

logout 继续增加 `session_version`，旧 Cookie/Bearer 即刻失效；账号 DISABLED 后已有 token 同样被 principal 校验拒绝。

### 审计

认证事件包括：

- `AUTH_LOGIN_FAILED`；
- `AUTH_LOGIN_LOCKED`；
- `AUTH_LOGIN_BLOCKED`；
- `AUTH_LOGIN_UNLOCKED`；
- `AUTH_LOGIN`；
- `AUTH_LOGOUT`。

允许记录 user_id、failure_count、locked_until、reason code、request_id、来源 IP、User-Agent。禁止记录密码、raw JWT、Cookie、Authorization、Secret 或手机号明文。
