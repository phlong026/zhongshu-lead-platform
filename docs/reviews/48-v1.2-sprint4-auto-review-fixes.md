# 48 - V1.2 Sprint 4 自动代码评审问题修复

- 来源 PR：`#33`
- 修复分支：`feature/v1.2-sprint4-supplier-rewards`
- 目标分支：`release/v1.2.0`
- 范围：3 个 P2 评审问题
- 结论：待最新 PR 全量 CI 通过后关闭

## P2-01：小时结算只处理首批到期奖励

### 问题

小时调度原先只调用一次 `run_due_supplier_reward_settlement(limit=500)`。积压超过 500 条时，后续到期奖励要等待下一小时；若最老记录持续失败，还会反复占用首批名额。

### 修复

新增 `drain_due_supplier_reward_settlement`：

- 每批最多 1,000 条；默认每批 500 条。
- 同一轮每个奖励最多尝试一次。
- 失败记录保留 `OBSERVING`，下一小时重试，但本轮不阻塞后续有效奖励。
- 默认最多 20 批，即每个小时周期最多处理 10,000 条。
- 返回批次数、唯一尝试数、结算/冻结/失败数量及安全上限状态。
- Scheduler 与 CLI 均改用排空函数。

新增测试使用每批 1 条模拟“最老记录永久失败、后两条正常”，验证正常奖励仍在同一轮全部结算。

## P2-02：接收方历史重复仍使用环境变量 365 天

### 问题

手机号提交去重已经读取已发布窗口，但派发候选和领取复检仍使用 `settings.lead_historical_suspect_days`，导致规则发布后两条链路口径不一致。

### 修复

- `_receiver_duplicate_assignment` 解析当前已发布 `SupplierRewardRule`。
- 截止时间改为 `当前时间 - rule.historical_suspect_days`。
- 候选公司批量计算时只解析一次规则并复用。
- 人工派发和领取复检均通过同一方法使用发布窗口。

新增测试发布 30 天历史窗口，并放置一条 45 天前同接收方领取记录，验证候选公司不再被旧 365 天窗口错误排除。

## P2-03：历史奖励迁移后规则快照为空

### 问题

`0004` 原实现仅增加非空 JSON 字段并默认 `{}`。升级前已存在的奖励缺少可审计规则内容，与“不可变规则快照”目标不一致。

### 修复

迁移在新增字段后逐行回填：

- 使用每条历史奖励已有的 `reward_ratio_bps`。
- 使用每条历史奖励已有的 `rule_version`。
- 明确记录历史实现无最低/最高限制。
- 明确记录当时冻结默认窗口 90/180/365 天。
- 标记 `legacy_backfill=true`，不伪造配置 ID 或生效时间。

迁移测试调整为：

1. 升级到 `0003`。
2. 插入一条比例 2750 基点、规则版本 7 的历史奖励。
3. 升级到 `head`。
4. 验证快照比例、版本、窗口和历史回填标记。
5. 降级回 `0001_initial`。

## 质量与风险结论

- 排空任务有明确安全上限，不会无限循环。
- 失败奖励不会在同一轮重复消耗批次额度。
- 配置化窗口在提交去重、派发候选和领取复检三处统一。
- 历史快照只记录可证明的既有字段和当时代码默认值，不推测历史配置。
- 新奖励仍由领取事务在插入前冻结最新已发布规则。

未发现新增 Critical 或 High 风险。
