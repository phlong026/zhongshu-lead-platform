# 45 - V1.2 Sprint 2 待派发、人工派发与领取评审

- 分支：`feature/v1.2-sprint2-dispatch-claim-backend`
- 目标分支：`release/v1.2.0`
- 任务：T14-T17
- 结论：待 PR 全量 CI 通过后可合并

## 1. 实现范围

### T14 待派发池

- 新增 V1.2 待派发池 API，仅查询 `READY_DISPATCH` 且 `current_assignment_id IS NULL` 的客资。
- 支持地区、来源类型和分页筛选。
- 池内手机号只返回脱敏值。

### T15 候选公司筛选

候选公司逐项校验：

1. 公司处于启用状态。
2. 具备已批准且启用的 `LEAD_RECEIVER` 能力。
3. 服务区域已批准、已启用且与客资地区精确匹配。
4. 供应商公司不得接收自己上传的客资。
5. 当前接收方在 365 天内不存在同手机号历史领取记录。
6. 可用积分扣除待领取预留后足以覆盖本次领取价格。

运营可查看资格、排除原因和本次领取价格；只有积分读取权限或超级管理员可查看精确余额、预留和可用积分。

### T16 人工派发

- 只提供人工选择公司接口，不包含自动、随机、轮询、权重或抢单逻辑。
- 幂等键与目标客资/公司绑定，重复请求返回原派发单，跨目标复用返回冲突。
- 锁定客资、公司和积分账户后重新执行候选校验，防止并发派发重复预留积分。
- 派发不扣积分，仅形成 `PENDING_CLAIM` 预留。
- 新增 PostgreSQL/SQLite 部分唯一索引：同一客资最多存在一个有效派发单。

### T17 领取原子事务

同一数据库事务中完成：

1. 锁定派发单、客资与积分账户。
2. 重新校验公司能力、服务区域、自供自领、历史重复、有效期和积分余额。
3. 扣除积分并写入唯一幂等流水。
4. 更新派发单与客资状态。
5. 固化 `appeal_deadline_at` 和 `reward_due_at`，两者均为领取时刻加 3 个工作日。
6. 解锁完整联系方式。
7. 对其他公司领取的供应商客资创建奖励观察快照。

平台手工客资不创建供应商奖励记录。供应商奖励比例当前按 V1.2 冻结默认 30% 快照；比例上下限和规则版本配置在 T22-T25 完成。

## 2. 评审发现与修复

### F-01 待派发池可能展示残留订单客资

- 原因：仅按 `READY_DISPATCH` 查询，未检查 `current_assignment_id`。
- 修复：池查询与候选详情均要求当前派发引用为空。

### F-02 并发派发可能重复使用同一积分余额

- 原因：派发前计算预留积分时未锁接收方公司/积分账户。
- 修复：人工派发按“客资锁 → 公司锁 → 积分账户锁”执行并重新计算预留。

### F-03 查询候选公司产生写操作

- 原因：旧积分可用量函数会在账户不存在时自动建账。
- 修复：V1.2 候选查询改为纯读取；缺失账户按余额 0 处理。

### F-04 候选接口默认暴露精确积分余额

- 修复：运营默认只看到是否积分不足；精确余额仅向 `points.read` 或 `*` 返回。

### F-05 已释放/过期但从未领取的订单可能解锁手机号

- 原因：详情页原逻辑对所有非 `PENDING_CLAIM` 状态显示明文。
- 修复：仅 `CLAIMED`、`FOLLOWING`、`RETURN_PENDING`、`COMPLETED` 解锁。

### F-06 SQLite 时间字段可能触发朴素/时区时间比较异常

- 修复：领取过期校验统一通过 `as_utc` 归一化。

### F-07 服务层约束不足以阻止跨进程双派发

- 修复：新增 `0003_v12_active_assignment_constraint` 部分唯一索引；迁移前检查历史重复有效订单并给出明确阻断信息。

## 3. 安全与账务边界

- 派发前不返回明文手机号。
- 未领取、已释放、已退回或已过期订单不解锁联系方式。
- 积分流水使用固定业务幂等键 `v12-claim:{assignment_id}`，只新增不修改。
- 领取重复调用不会再次扣分或重复创建奖励。
- 自供自领在候选筛选、派发执行和领取执行三个节点硬阻止。
- 供应商奖励记录通过 `assignment_id` 唯一约束防重复。

- 朴素时间过期校验。

- 数据库部分唯一索引的元数据与 Alembic 升降级。
