# V1.2 五角色统一工作台文档综合评估

日期：2026-08-25
评估对象：`DESIGN.md`、`docs/plan/V1.2五角色统一工作台开发清单.md`，以及当前仓库实现。
结论：业务目标和页面职责已具备可实施方向，但当前仍是“设计/任务已定义”，不是“代码已实现”或“可上线”。六项 P0 技术合同是页面开发与生产上线的强制门槛；实施必须以现有已验证能力为基线，只补真实缺口，不重复建设派发、领取、退回核验、积分、审计和通知能力。

## 1. 已明确且一致的部分

- 角色收敛为五类；电销只提交事实结论，运营做业务处置，超级管理员做资金动作。
- 电销任务只能由运营管理员派发或改派；电销不得自主领取、转派或从公共队列取任务。
- 超级管理员与运营管理员均可开通、启用、停用和绑定加盟商负责人/员工账号；超级管理员的每一次该类操作必须留存理由、前后状态和高风险审计。
- 加盟商员工与负责人均可直接供资；负责人可在本公司内分配、回收已领取客资，无需运营审批。
- 运营只看加盟商公司的业务状态、数量与异常汇总，不得查看员工之间的分配明细；公司内部操作仍保留审计记录，供超级管理员按理由追溯。
- 所有角色都有移动入口：超级管理员/运营使用新增 `/h5/admin/`，电销使用 `/h5/call/`，加盟商使用 `/h5/`。
- H5 底栏均以“首页”开头，待办为首页首个模块，标签统一两字。
- 新后台禁止跳旧页；客资详情必须提供全流程时间线。
- 超级管理员资金操作无需二次复核，但必须保留理由、凭证、流水、审计和异常告警。

## 3. 文档还需完善的内容

### P0：六项强制技术合同

下列六项必须同时完成技术设计、测试草案和与现有能力的差距映射，才能开始对应页面开发；六项均通过预发布验证，才能允许生产上线。每一项都应优先复用现有已验证的模块，禁止为追求形式完整而重写已有派发、领取、退回核验、积分流水、审计或 Outbox 通知。

1. **五角色、数据范围与账号生命周期合同**
   - 将现有多角色矩阵映射为五个业务角色，明确每个角色对账号、公司、客资、派发、任务、积分和审计的读取/写入范围。
   - 电销仅能处理运营派发给本人的任务；运营负责派发、改派和业务处置。
   - 运营与超级管理员都可管理加盟商负责人/员工账号；超级管理员操作须有理由、前后值及高风险审计。

2. **唯一客资状态机与双电销任务合同**
   - 明确状态、责任人、允许动作、必填理由/证据、SLA、幂等与并发规则。
   - 新增前置电销任务，与既有退回事实核验严格分型、分队列、分结论；复用既有通话鉴权和审计链路，不共用业务状态。

3. **员工—派发单公司内部协作合同**
   - 以已领取派发单为公司内部归属对象，明确负责人分配、回收、转交、员工停用、负责人变更及审计事件。
   - 运营仅看公司级状态、数量和异常汇总，不看员工个人分配明细，也不参与审批；超级管理员仅在有理由时审计查询内部明细。

4. **积分、奖励与退回一致性合同**
   - 复用既有不可变流水、退款、奖励冻结和冲正能力，补足领取、退回终审、奖励调整间的原子性、幂等和日对账。
   - 超级管理员可直接执行资金动作，无需二次复核；每次必须具有原因、关联业务单、前后余额、凭证说明、审计和异常告警。

5. **移动入口、认证与旧页退出合同**
   - 固化 `/admin/`、`/h5/admin/`、`/h5/call/`、`/h5/` 的角色入口、会话回跳、无权表现、通知深链接和登出地址；`/call/` 只作兼容跳转，`/m/` 不引入。
   - 列出每个旧菜单、深链接、写接口的迁移去向；新壳不再跳转 `index.html#/...`，旧页先只读/重定向，验证完成后再删除写入口。

6. **迁移、回滚与验收合同**
   - 每个存量账号人工确认角色映射；迁移采用导出、dry-run、备份、写入、对账、回滚六步，任何未识别账号不得自动提权。
   - 发布验收同时覆盖 COS 证据读写、微信真实通知、五角色 UAT、审计可追溯和恢复演练。

#### 已有合同必须细化的内容

1. **员工与公司内部分配数据模型**
   - 明确负责人向员工分配的是“派发单”“客资”还是“跟进任务”；建议以派发单为唯一归属对象。
   - 定义字段、迁移步骤、回收/转交、员工离职、负责人变更和审计事件。
   - 运营不可查看员工个人操作详情的边界，应同时保留公司级派发状态和异常汇总，避免平台完全失去业务可观测性。

2. **前置电销核验合同**
   - 明确任务类型、联系结果、事实结论、结论必填项、可重开条件、超时升级和运营可选处置。
   - 仅允许运营派发/改派；与退回核验使用同一通话与审计组件，但不能共享状态或互相误入队列。

3. **移动入口与认证合同**
   - 明确 `/h5/admin/` 与 `/h5/call/` 的静态目录、登录入口、无权访问表现、登录后回跳、通知深链接和移动端退出地址；`/call/` 仅作兼容重定向。
   - 现有加盟商 H5 登出仍回到旧 `admin/index.html`，与新规则冲突：`apps/h5/public/v12-workbench.js:41`。必须改为角色匹配的新登录/入口页。

4. **角色迁移与数据回滚合同**
   - 对每个现有账号给出人工确认的角色映射；不得根据名称自动提权。
   - 迁移必须分为预演、备份、写入、对账和回滚五步。

### P1：功能与风险补强

1. **隐私与号码最小暴露**：运营只看脱敏号码；完整号码仅本人、本人任务、核验中时交给电销。管理员的紧急查看应有单独理由和审计。
2. **超级管理员直接资金操作的补偿控制**：不可变流水、操作理由、凭证编号、余额前后值、日对账、异常阈值告警、冲正而非删除。
3. **通知合同**：每一个状态转换明确收件人、模板、站内/微信渠道、深链接、失败重试和人工补发责任人。
4. **旧页退出映射表**：每一个旧菜单、深链接和写接口都要有“迁入新页、只读历史、重定向或删除”的明确结论，不能仅全局搜索后删除。
5. **全流程详情的查询性能**：时间线应分页/按需加载，避免一次查询一条客资全部关联审计和通知造成慢页。

### P2：体验和交付完整性

1. 为移动端写出离线/弱网时表单草稿、证据上传进度、重复提交和失败恢复策略。
2. 为桌面与移动分别定义关键页面尺寸：390×844、768×1024、1440×900。
3. 为每个角色提供空态、无权态、加载态、操作成功回执和错误重试文案。
4. 建立真实业务 UAT 脚本：五角色、两类来源、两类电销任务、领取、退回、退款、奖励、通知和全流程追溯。

## 4. 移动端拨号评估

- **当前已实现**：电销本人、核验中的退回任务可点“一键拨号”；后端鉴权并写审计后返回 `tel:`，前端跳转至系统拨号盘。`apps/api/src/routers/v12_returns.py:412`、`apps/call-h5/public/app.js:415`。
- **应扩展**：前置电销核验复用该能力；电销移动端“核验”页在任务开始后显示拨号按钮。
- **不能承诺**：H5 静默自动外呼、自动接通、后台录音。它们需要用户确认或独立原生/云外呼能力，并涉及额外权限、供应商、费用与合规。

以下六项必须有可评审技术设计、测试草案和“现有能力/补齐缺口”对照表，才能开始对应页面编码；六项全部完成预发布验证前，不得标记生产上线：

- [ ] 五角色、数据范围与账号生命周期合同；
- [ ] 唯一客资状态机与双电销任务合同；
- [ ] 员工—派发单公司内部协作合同；
- [ ] 积分、奖励与退回一致性合同；
- [ ] `/h5/admin/`、`/h5/call/` 移动入口、鉴权、旧页退出、兼容重定向和深链接方案；
- [ ] 角色迁移、回滚、COS/微信外部验收与五角色 UAT 合同。

执行中必须优先接入现有已验证能力；若现有接口与合同一致，则仅补测试、权限/数据范围和页面接入，不得平行重建。六项中任一项未完成时，可继续做不改变业务状态的视觉稿或静态原型，但不得把页面视为完整业务交付或生产可上线版本。
