## 2. 逐条核实

### P1-1 员工可通过旧接口越权读取客资、派发单与领取详情

**判定：属实。范围比原报告更大——前两个接口是跨公司可读，不只是"同公司不同员工"。**

角色前提：`services/rbac.py:70-80` 确认 `FRANCHISE_EMPLOYEE` 是独立角色，
不包含 `FRANCHISE_OWNER`，因此所有 `has_any_role("FRANCHISE_OWNER")` 判断对员工全部落空。

| 接口 | 位置 | 实际校验 | 员工可达范围 |
|---|---|---|---|
| `GET /leads/{id}` | `routers/leads.py:132-137` | 仅 `FRANCHISE_OWNER` 走 Assignment 归属校验 | **任意公司任意客资** |
| `GET /dispatch/assignments/{id}` | `routers/dispatch.py:100-101` | 仅 `FRANCHISE_OWNER` 校验 `company_id` | **任意公司任意派发单** |
| `GET /claims/assignments/{id}` | `routers/claim.py:29-34` → `services/claim_service.py:73-75` | 仅校验 `company_id` 相同 | 同公司任意员工 |

**数据暴露精度（原报告表述准确，此处固化证据）：**

- `services/lead_service.py:44` 的 `lead_to_dict` 按 `lead.phone.read` / `lead.own.phone.read` / `*`
  判定是否返回明文手机号。`FRANCHISE_EMPLOYEE` 三者皆无 →
  `GET /leads/{id}` **只返回掩码号**，另泄露姓名、城市、需求摘要、预算。
- **完整手机号仅在 `own_assignment_detail` 泄露**：`services/claim_service.py:77` 直接
  `decrypt_text(lead.phone_encrypted)` 且不做任何权限判定，`:95` 在 `unlocked` 时输出明文，
  `:99` 同时输出公司积分余额（balance / reserved / available）。
- `assignment.lead_snapshot`（`services/dispatch_service.py:115-126`）**不含手机号**，
  仅含姓名、城市、区县、品类、来源、需求摘要、预算。

**不要误改：**`GET /dispatch/assignments` 列表接口（`routers/dispatch.py:79-83`）**当前是安全的**——
员工既非 `FRANCHISE_OWNER`，又不具备 `assignment.read`，会正确返回 403。修复时勿一并改坏。

**修复要求：**

1. `leads.py:132-137`：把 `FRANCHISE_OWNER` 专用分支改为对**所有加盟商侧角色**生效的归属校验；
   员工须额外满足 `Assignment.internal_assignee_user_id == principal.user_id`。
2. `dispatch.py:100-101`：同上，补公司维度 + 员工归属维度校验。
3. `claim_service.py:73-75`：复用 `services/company_assignment_v12.py:29` 的
   `require_company_assignment_access()`，替换裸 `company_id` 比较。

**验收标准：**

- 跨公司请求上述三个接口返回 403/404，不返回任何业务字段。
- 同公司但非 `internal_assignee_user_id` 的员工请求返回 403。
- `GET /dispatch/assignments` 列表对员工仍返回 403（回归不被破坏）。
- 负责人（`FRANCHISE_OWNER`）对本公司数据的既有访问不受影响。

### P2-2 员工可读取平台全局经营汇总与预警

**判定：属实。定级由 P1/P2 下调为 P2；但影响面比原报告更大。**

- `routers/admin.py:45-58`：`/dashboard/summary` 的权限白名单在 `:54` 包含 `h5.home`，
  而 `h5.home` 同时授予 `FRANCHISE_OWNER`（`rbac.py:57`）与 `FRANCHISE_EMPLOYEE`（`rbac.py:73`）。
- `services/admin_service.py:38-54`：先无条件计算**全平台** `business` 指标
  （总客资数、待派发、领取率、跟进率、转化率、活跃公司数等）。
- `services/admin_service.py:95-104`：**仅在 `has_any_role("FRANCHISE_OWNER")` 时**才覆盖为本公司口径。
  员工不满足该条件 → 拿到全平台数据。

**定级下调理由：**泄露的是聚合计数，不含客户 PII、不含资金。
`finance` 块有独立门禁（`admin_service.py:57` 需 `dashboard.finance.read` / `points.read` / `*`），
员工无法获取。与 P1-1 的完整手机号不是同一量级。

**影响面扩大：**`routers/admin.py:99-103` 的 `/dashboard/alerts`
**只拦截 `FRANCHISE_OWNER`，没有任何权限校验**——
`FRANCHISE_EMPLOYEE` 与 `TELESALES` 角色同样可读平台预警。

**修复要求：**

1. `admin.py:54`：从 `/dashboard/summary` 白名单移除 `h5.home`，
   或在 `admin_service.dashboard_summary` 中把公司口径分支的条件
   从 `has_any_role("FRANCHISE_OWNER")` 放宽为**所有加盟商侧角色**（含员工），
   并对员工进一步收敛到本人口径。
2. `admin.py:99-103`：`/dashboard/alerts` 补显式权限校验
   （建议 `dashboard.operation.read` / `*`），不要只靠角色黑名单。

**验收标准：**

- 员工与电销请求 `/dashboard/summary`，返回值中不含任何跨公司聚合数。
- 员工与电销请求 `/dashboard/alerts` 返回 403。
- 运营与超管的既有看板数据不变。

### P2-3 员工退回记录的统计与访问范围不一致

**判定：属实。**

| 用途 | 位置 | 口径 |
|---|---|---|
| 报表统计 | `routers/v12_insights.py:795-802` | `submitted_by == 本人` **OR** `assignment 当前分配给本人` |
| 列表查询 | `routers/v12_returns.py:235-245` | `company_id` **AND** `assignment 当前分配给本人` |
| 详情/证据下载 | `_can_read_return` → `services/company_assignment_v12.py:29-41` | 员工必须是 `internal_assignee_user_id` |

报表侧多出 `submitted_by` 这一分支，访问侧三处均无。
负责人在退回处理过程中收回或转派后，**原提交员工报表仍有计数，但列表打不开、无法补证**。

**修复要求：**统一"本人"定义。建议以**原提交人始终可查看、补证、重提**为准，
即在 `v12_returns.py:235-245` 与 `company_assignment_v12.py:29-41`
的员工分支补入 `ReturnRequest.submitted_by == principal.user_id` 的 OR 条件。

**验收标准：**员工提交退回后由负责人转派给他人，该员工仍可打开该退回单并补充材料；
报表计数与列表条数一致。

### P2-4 公司站内消息全员可见并共享已读状态

**判定：属实。**

- `routers/notifications.py:36-37`：查询条件为
  `user_id == 本人` **OR** (`user_id IS NULL` **AND** `company_id == 本人公司`)
  → 公司级消息（`user_id` 为空）投递给同公司全部员工。
- `core/models.py:534-546`：`Notification` 表**只有单一 `read_at` 列**，
  无 per-user 已读关联表。
- `routers/notifications.py:55-63`：`mark_read` 直接写这一行的 `read_at`
  → 任一员工点击已读，负责人与其他员工看到的同一条消息一并变为已读。

**修复要求：**业务消息在生成时展开到具体收件人（每人一行 `Notification`），
或新增 `notification_reads(notification_id, user_id, read_at)` 关联表，
已读状态按用户独立保存。前者改动更小且与"员工只看本人"方向一致。

**验收标准：**同公司两名员工各自的未读数互不影响；
员工只看到与本人相关的业务消息。

### P2-5 运营首页电销待办混入退回核验任务

**判定：属实。**

- `core/models_v12.py:85`：`task_type` 列真实存在（扩展挂载到 `VerificationTask`）。
- 写入侧已正确区分：`services/pre_dispatch_v12.py:140,213` 写 `PRE_DISPATCH_VERIFY`；
  `services/return_v12.py:353` 写 `RETURN_VERIFY`。
- `routers/v12_insights.py:177-194`：`_management_overview` 的四个 verification 指标
  （`verification_pending` / `verification_in_progress` /
  `verification_awaiting_operation` / `verification_overdue`）
  **全部只按 status 过滤，无 `task_type` 条件**。
- `apps/admin/public/v12-operations.js:174-176`：
  「电销处理中」「待运营处置」两张卡片点击后跳转 `?view=telesales`，
  而 `routers/v12_pre_dispatch.py:141` 只列出 `PRE_DISPATCH_VERIFY`
  → 数字包含退回核验，列表不包含，必然对不上。

**修复要求：**`v12_insights.py:177-194` 四个指标补 `task_type` 过滤，
按前置核验与退回核验分别统计并分别输出字段；前端卡片按类型跳对应页面。

**验收标准：**造出 1 条 `RETURN_VERIFY` 进行中任务，
运营首页「电销处理中」计数不变；退回核验计数单独可见且点击进入退回页。

### P3-6 候选公司接口一次返回所有公司

**判定：属实。**

- `routers/v12_dispatch.py:190-214`：`dispatch_candidates` 无任何分页参数，
  直接 `list_candidates(db, lead=lead)` 后全量序列化返回。
- `services/dispatch_v12.py:330-363`：`company_stmt` 经四路 `outerjoin`
  后 `db.execute(...).all()`，**无 limit / offset**。

**补充（原报告未指出）：**该查询是先把 **Company 全表**取出再逐个计算接单资格，
成本随加盟商总数线性增长，**与该公司是否有资格接单无关**。

**修复要求：**默认返回 top-N（建议 N=20，按现有排序规则），
提供服务端搜索与"查看更多"分页。

**验收标准：**公司数扩大到 1000 条量级时，派发弹窗首屏响应时间不随之线性劣化。

## 3. 建议修复顺序

1. **P1-1** 三个旧接口的归属校验（跨公司 + 员工归属两个维度），并补回归测试。
2. **P2-2** `/dashboard/summary` 与 `/dashboard/alerts` 一并修（同文件同类问题，拆开无收益）。
3. **P2-3** 统一退回记录"本人"定义为原提交人始终可访问。
4. **P2-4** 业务消息展开到具体收件人；已读状态按用户独立保存。
5. **P2-5** 运营首页按 `task_type` 分开统计并分别跳转。
6. **P3-6** 候选公司改 top-N + 服务端搜索，单独排期。
