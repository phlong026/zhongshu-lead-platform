- 分支：`feature/v1.2-sprint4-supplier-rewards`
- 目标分支：`release/v1.2.0`
- 任务：T22-T25
- 结论：待 PR 全量 CI 与自动代码评审通过后可合并

## 1. 实现范围

### T22 奖励状态与规则快照

- 新增版本化供应商奖励规则：
  - 奖励比例（基点）；
  - 奖励最低积分；
  - 奖励最高积分；
  - 硬重复、奖励重复、历史疑似窗口；
  - 规则版本、配置 ID 与生效时间。
- 新奖励在领取事务中自动冻结当时已发布规则快照。
- 奖励积分按 `floor(实际领取扣分 × 比例)` 计算，再应用最低值和最高值。
- 已存在奖励不随新规则发布而回算，保证历史账务可审计。
- 已发布去重窗口同时用于后续手机号重复检测，并在去重事件中保存规则版本和窗口快照。

### T23 到期结算

- 仅 `OBSERVING` 且达到 `reward_due_at` 的奖励可结算。
- 结算前再次检查有效申诉；存在申诉时转为 `FROZEN`，不记账。
- 无有效申诉时：
  - 给供应商积分账户入账；
  - 写入 `REWARD` 类型不可变积分流水；
  - 使用 `v12-reward:{reward_id}:settle` 幂等键；
  - 奖励进入 `SETTLED`。
- Scheduler 在启动时执行一次，之后每小时执行一次。
- CLI 支持 `supplier-rewards` 独立任务与 `all` 聚合任务。
- 申诉被驳回且奖励截止已经到期时，在同次业务事务提交前立即结算，不等待下一小时任务。

### T24 异常冲正

- 仅 `SETTLED` 奖励可冲正。
- 原因仅允许：
  - `FRAUD`
  - `SYSTEM_ERROR`
  - `ADMIN_ERROR`
- 冲正写入关联原奖励流水的 `REVERSAL` 反向流水。
- 使用 `v12-reward:{reward_id}:reverse` 幂等键。
- 供应商已消费奖励积分时仍可冲正，账户可形成负余额债务，避免账务事实无法恢复。
- 普通退回不得使用 `REVERSED`，仍走观察期冻结/取消流程。

### T25 规则配置

- 规则存储于版本化 `SystemConfig`：`domain=supplier_reward`、`key=default`。
- 支持草稿创建、发布和历史规则退休。
- 同一时点只解析最新已发布且已生效的规则。
- 规则发布只影响之后创建的奖励和之后执行的去重判断。
- 创建、发布、结算、批量结算和冲正均记录审计。

## 2. 状态机复核

允许路径：

- `WAITING_CLAIM → OBSERVING`
- `OBSERVING → FROZEN`
- `FROZEN → OBSERVING`
- `OBSERVING → SETTLED`
- `OBSERVING/FROZEN → CANCELLED`
- `SETTLED → REVERSED`

禁止路径：

- `OBSERVING → REVERSED`
- `FROZEN → SETTLED`（必须先确认申诉已驳回并恢复观察）
- `CANCELLED → SETTLED`
- `REVERSED → SETTLED`

## 3. 事务、并发与幂等

- 单笔结算锁定奖励记录并通过积分账户行锁写账。
- 批量任务逐奖励使用 SAVEPOINT，单条失败不回滚其他成功结算。
- 结算前执行有效申诉二次检查，降低任务与申诉并发时错误入账风险。
- 申诉驳回后的即时结算与驳回状态、订单恢复处于同一外层事务。
- 结算和冲正均先查询幂等流水，重复调用不会重复改变积分。
- `supplier_lead_rewards.assignment_id` 唯一约束继续阻止同一领取产生多条奖励。

## 4. 权限与数据隔离

- 供应商公司只能查看本公司奖励和汇总。
- 内部 `reward.read` 可查看奖励数据。
- `reward.manage` 可管理规则与执行结算。
- `reward.reverse` 单独控制异常冲正。
- 规则管理和异常冲正均标记为敏感权限。
- 奖励接口不返回客户明文手机号。
- 积分账户精确余额继续通过既有积分权限和接口隔离。

## 5. 数据迁移

- `0004_v12_reward_rule_snapshot` 为奖励表增加非空 JSON 规则快照字段。
- 历史奖励默认快照为空对象，不伪造历史规则事实。
- 新奖励由应用层在插入前写入完整规则快照。
- 升级与降级纳入 SQLite 迁移往返测试；生产 PostgreSQL 仍需在 T33 使用脱敏快照演练。

## 6. 评审发现与修复

### F-01 有效申诉冻结可能被 SAVEPOINT 回滚

- 原因：结算函数若设置 `FROZEN` 后抛出异常，批量任务的嵌套事务会回滚冻结更新。
- 修复：冻结作为正常结算结果返回，批量任务记录 `frozen` 数量并提交状态变化。

### F-02 规则发布后领取仍使用硬编码 30%

- 原因：原领取服务在 Sprint 2 中固定写入 3000 基点。
- 修复：在奖励记录插入前解析已发布规则，覆盖比例、积分、版本和快照，保持领取事务原子性。

### F-03 去重窗口配置未进入实际引擎

- 原因：原去重引擎只读取环境变量默认值。
- 修复：提交/初审复检时解析已发布规则，并在去重事件中记录规则来源与窗口。

### F-04 申诉驳回后到期奖励需立即结算

- 原因：仅依赖小时任务会产生最长一小时延迟。
- 修复：监听 `FROZEN → OBSERVING` 且已到期的奖励，在外层事务提交前执行结算。

### F-05 调度部署测试误判 Compose 结构

- 原因：生产配置采用基础 Compose + 生产覆盖文件，而不是在覆盖文件重复声明命令或使用 `extends`。
- 修复：合约测试分别校验基础文件中的入口与覆盖文件中的生产调度服务/安全配置。
