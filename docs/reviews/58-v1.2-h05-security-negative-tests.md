## 首轮代码盘点发现

### 1. 跨租户证据上传存在对象存储副作用

`v12_returns.upload_return_evidence` 原实现读取并保存文件后才进入 `add_return_evidence` 的公司权限校验。攻击者只需拥有合法 `return.own.manage` 权限并猜到其他公司的 return UUID，就可能在最终 403 之前产生孤儿对象。

修复：ReturnRequest 存在性校验后立即检查 `principal.company_id == item.company_id`，在任何 `file.read()`、MIME 处理和 storage save 之前 fail-closed。

### 2. 停用公司成员旧 JWT 仍可成为 Principal

`get_current_principal` 原实现检查 User ACTIVE 和 session_version，但未检查绑定 Company 状态。公司停用后，成员旧 JWT 仍可通过 `/auth/me`，部分不调用 `require_active_company` 的接口也可能继续访问。

修复：用户存在 `company_id` 时，Principal 构建前必须确认 Company 存在且 `status == ACTIVE`；否则统一 `AUTH_INVALID`。

9. JWT tamper / expiry / stale session_version / disabled company；
10. OAuth state tamper / expiry / open redirect / invite replay / cross-company binding；
11. Points adjustment privilege、idempotency、negative balance；
12. Return final-review / reward settle / reverse 权限；
13. Reward duplicate settlement single-ledger invariant；
14. Audit before/after/metadata credential/phone redaction。

## 数据副作用要求

Unauthorized 不仅要返回 403/404，还必须满足：

- 不创建对象存储文件；
- 不创建 ReturnEvidence；
- 不修改积分余额；
- 不生成重复 Reward Ledger；
- 不修改其他公司的 Notification read_at；
- 错误正文不包含目标手机号、姓名、说明或财务摘要。
