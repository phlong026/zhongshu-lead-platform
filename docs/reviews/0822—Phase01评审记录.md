## 4. 发现清单

严重度：CRITICAL 为安全/数据缺陷或功能阻断；P2 为应整改；P3 为改进项。置信度 1-10（≥7 已实证或代码逐行核验）。标注「多方确认」= 至少两个独立评审通道（主审/子代理/Codex）得出同一结论。

### CRITICAL

**C1（置信 8/10，已实证）`apps/api/src/routers/auth.py:113-119` — `return_url` 前缀黑名单可被 ASCII 控制字符绕过，形成认证后开放重定向**

- 机制：`_sanitize_return_url` 仅拒绝 `//`、`/\`、`\` 前缀。实测 `"/\t/evil.com"`、`"/\t//evil.com"`、`"/\n//evil.com"` 均原样放行。WHATWG URL 规范要求浏览器解析前剥离 tab/LF/CR，故 `Location: /\t/evil.com` 在浏览器中等价于 `//evil.com`（跨域）。提交态 `wechat_callback` 将该值直接写入 `RedirectResponse(url=return_url)`，且此刻已种下会话 Cookie。
- 攻击面：`GET /api/v1/auth/wechat/start?return_url=%2F%09%2Fevil.com` 为可外链投递的 GET；亦可通过 confirm-start 的 `return_url` 注入。
- 修复建议：本系统合法 `return_url` 全部以 `/h5/#/` 开头，直接改为**前缀白名单**（不以 `/h5/` 开头一律回落默认值），并拒绝包含任何 ASCII 控制字符（0x00-0x1F、0x7F）或反斜杠的输入；对 `Location` 值做 percent-encode 后输出。
- Phase 0 关联缺口：`return_url` 收敛测试只断言了 `https://evil.example/steal` 与 `/\evil.com` 两个变体（`test_wechat_oauth.py:136-153`），应补控制字符负例。

**C2（置信 9/10，已实证，本次变更引入的功能回归）已绑定用户会话丢失后永久无法重新登录 H5，且无任何恢复路径**

完整证据链（每环均已在提交态代码核验）：

1. H5 登录按钮强制要求 URL 携带邀请：`apps/h5/public/app.js:49` `if(!invite){toast('请使用平台发出的专属邀请链接'...);return;}`；契约测试进一步锁死三脚本中不得出现 `/auth/wechat/start`（`test_frontend_contract.py:94`），普通登录在前端无入口。
2. 后端本支持无邀请的幂等重登（legacy state → 已有 identity → 登录），但前端不可达。
3. 过去的恢复路径是「管理员给已绑定公司重发邀请 → 用户点开 → 幂等登录」：**旧版** `create_company_invite`（e0357ae）无 `primary_user_id` 检查，允许重发；**新版** `auth_service.py:246-248` 对已绑定公司抛 `AUTH_COMPANY_ALREADY_BOUND`，路径被封死。
4. 全仓不存在解绑/换绑 API（grep `primary_user_id` 的全部写点：绑定占用 `auth_service.py:421`、bootstrap 种子 `bootstrap.py:176`，无管理端重置入口）。
5. H5 状态页反而提示「请联系平台管理员执行换绑并留痕」（`status-pages-v13.js` bound_other 文案）——承诺了不存在的能力。

影响：加盟商负责人退出登录、更换设备、清 Cookie 或 token 过期（Cookie `max_age=jwt_expire_minutes*60`）后，整个 H5 渠道对其不可用，只能人工改库恢复。
修复方向（任选或组合）：① H5 登录页为无邀请场景提供普通微信登录入口（后端已支持）；② 提供带审计的管理端换绑/解绑闭环（与状态页文案对齐）；③ 放宽为已绑定公司重发「登录型」邀请。同时补一条「已绑定用户无邀请重登」的端到端测试。
