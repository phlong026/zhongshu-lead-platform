## 4. 发现清单

严重度：CRITICAL 为安全/数据缺陷；P2 为应整改；P3 为改进项。置信度为 1-10（≥7 已实证或代码逐行核验）。

### CRITICAL

**C1（置信 8/10，已实证）`apps/api/src/routers/auth.py:113-119` — `return_url` 白名单可被 ASCII 控制字符绕过，形成认证后开放重定向**

- 机制：`_sanitize_return_url` 仅做前缀黑名单（`//`、`/\`、`\`）。实测 `"/\t/evil.com"`、`"/\t//evil.com"`、`"/\n//evil.com"` 均原样放行。WHATWG URL 规范要求浏览器解析前剥离 tab/LF/CR，故 `Location: /\t/evil.com` 在浏览器中等价于 `//evil.com`（跨域）。提交态 `wechat_callback` 将该值直接写入 `RedirectResponse(url=return_url)`，且此刻已种下会话 Cookie。
- 攻击面：`GET /api/v1/auth/wechat/start?return_url=%2F%09%2Fevil.com` 为可外链投递的 GET；亦可通过 confirm-start 的 `return_url` 注入。
- 修复建议：本系统合法 `return_url` 全部以 `/h5/#/` 开头，直接改为**前缀白名单**（不以 `/h5/` 开头一律回落默认值），并拒绝包含任何 ASCII 控制字符（0x00-0x1F、0x7F）或反斜杠的输入；对 `Location` 值做 percent-encode 后输出。
- Phase 0 关联缺口：步骤 5 相关的 `return_url` 收敛测试只断言了 `https://evil.example/steal` 与 `/\evil.com` 两个变体（`test_wechat_oauth.py::136-153`），应补控制字符负例。
