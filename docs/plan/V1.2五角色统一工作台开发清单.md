# V1.2 五角色统一工作台开发清单

状态：实施中（基于第一轮五角色 P0 上线基线增量开发）
日期：2026-08-25
设计依据：仓库根目录 `DESIGN.md`
范围：平台管理后台、H5 加盟商工作台、电销工作台，以及与其一致的 RBAC、状态机、审计、通知和资金边界。

## 1. 目标与不可突破的边界

### 1.1 唯一角色模型

系统只保留五类业务角色：

1. 超级管理员；
2. 运营管理员；
3. 电销人员；
4. 加盟商负责人；
5. 加盟商员工。

一个账号只能有一个业务主角色。超级管理员如需紧急接管，使用独立超级管理员账号，不与运营、电销或加盟商角色叠加。

### 1.2 权责规则

- 超级管理员：系统治理和全部资金动作，包括充值、调账、规则、奖励、流水与审计。
- 运营管理员：加盟商审核、账号生命周期、初审、派发、电销协同、异常处理和退回终审。
- 电销人员：仅接收运营管理员派发的事实核验任务并提交结论，不得自主领取、改派或决定业务最终结果。
- 加盟商负责人：负责本公司供资、领取、分配、跟进、退回、资料和人员申请。
- 加盟商员工：只处理明确分配给自己的客资、供资草稿和补证任务。

### 1.3 设计与导航规则

- V1.2 是唯一的新后台壳；新页面不得打开 `index.html#/...` 或其他旧页。
- H5 每个角色首个底栏都是“首页”；“待办”是首页的首要模块，而非独立底栏按钮。
- H5 底栏最多五项，所有标签固定两个字：
  - 超级管理员：`首页 / 治理 / 资金 / 我的`；
  - 运营管理员：`首页 / 客资 / 派发 / 异常 / 我的`；
  - 电销人员：`首页 / 核验 / 记录 / 我的`；
  - 加盟商负责人：`首页 / 接收 / 供资 / 跟进 / 我的`；
  - 加盟商员工：`首页 / 跟进 / 供资 / 我的`。
- 桌面端顶栏只保留刷新、设置（有权限时）和退出；身份资料放在左侧栏底部。
- 每个首页先显示角色待办，再显示最多四张可点击的关键指标卡；卡片必须进入对应的可处理列表。
- 任意业务详情必须显示来源、当前状态、当前责任人、下一步、截止时间和“查看全流程”。
- 开发必须先复用已验证的派发、领取、退回核验、积分流水、审计、Outbox 通知和 V1.2 组件；只补齐本清单中的真实差距，不以重写现有模块换取形式上的“完整”。

### 1.4 终端与入口分工

本项目的“应用端”是响应式 H5/微信内置浏览器页面，不是现有原生 App。所有角色都需要移动端入口；桌面端承接批量、复杂配置与长时间操作。

| 角色 | 应用端（移动 H5） | 桌面端 | 主使用场景 |
|---|---|---|---|
| 超级管理员 | `/h5/admin/`：风险待办、治理审批、资金动作、审计查询 | `/admin/`：完整系统治理、账号组织、规则、资金和审计 | 桌面主用，移动用于及时处置 |
| 运营管理员 | `/h5/admin/`：待办、单条初审、异常、退回终审、派发确认 | `/admin/`：客资队列、批量审核、派发、加盟商治理、追溯 | 桌面主用，移动用于即时处理 |
| 电销人员 | `/h5/call/`：任务、拨号、结论、记录 | `/h5/call/`：批量任务、复杂录入和历史检索 | 移动主用，桌面可用 |
| 加盟商负责人 | `/h5/`：接收、供资、跟进、人员申请、积分查看 | 同一 `/h5/` 响应式页面在浏览器使用 | 移动主用 |
| 加盟商员工 | `/h5/`：待办、跟进、供资、补证、消息 | 同一 `/h5/` 响应式页面在浏览器使用 | 移动主用 |

移动端拨号规则：电销点击“拨号”后，后端先校验任务归属、任务状态和电话查看权限，写入审计，再返回 `tel:` 地址；浏览器调起系统拨号盘并由用户确认拨打。网页/H5 不得在无用户点击的情况下静默自动接通电话。

## 3. 十一阶段开发任务

### 阶段 1：基线冻结、数据盘点与迁移护栏

- [ ] 导出现有账号、角色、公司、邀请、能力区域、积分账户、流水、在途客资、派发单、退回单和奖励快照。
- [ ] 隔离并逐项确认当前未提交改动；禁止覆盖未知工作内容。
- [ ] 建立迁移前数据库备份、可读对账报告和可回退发布标签。
- [ ] 写入角色迁移决策表：`FINANCE → SUPER_ADMIN`、`RETURN_REVIEWER → OPERATION`；`OWNER`、`LEAD_ENTRY` 必须人工逐账号确认后映射或停用。
- [ ] 新增迁移 dry-run，先报告变化，不写入生产数据。

验收：dry-run 能列出每个受影响账号的旧角色、新角色、公司关系和处理建议；任何未识别账号不会被自动提权。

### 阶段 2：五角色 RBAC 与账号生命周期

- [ ] 将权限矩阵收敛为五角色，删除正常业务入口中的 `OWNER`、`LEAD_ENTRY`、`FINANCE`、`RETURN_REVIEWER`。
- [ ] 改为一个账号一个业务主角色，并阻止组合角色创建、更新和登录进入混合工作台。
- [ ] 充值、调账、套餐、价格规则、奖励规则、冲正和资金流水只授予超级管理员。
- [ ] 将加盟商负责人/员工的创建、邀请、停用、启用和公司绑定授权给运营管理员；超级管理员拥有同等直接操作能力，每次操作必须记录理由、操作者、前后状态和审计事件。
- [x] 加盟商负责人仅可提交员工新增/停用申请、查看公司人员；不可创建权限、查看密码或直接停用账号。
- [ ] 员工停用后撤销会话，并对未完成任务提供转交或待交接状态。
- [ ] 加盟商员工可直接提交供资；加盟商负责人同样可直接提交供资。
- [ ] 初始密码仅在成功创建响应中一次性展示并可复制；不保存明文密码。

设计落实：平台桌面左侧栏底部增加身份卡；顶栏不显示账号/角色；账号详情使用中文岗位、状态、公司和操作历史，不显示原始权限码。

验收：五角色逐一登录，菜单、数据、按钮和 API 权限负例均符合边界；停用账号立刻不能继续使用旧会话。

### 阶段 3：唯一状态机与双电销任务模型

- [x] 定义并固化客资状态：草稿、待运营初审、待电销核验、待运营处置、待派发、已派发、已领取、跟进中、退回处理中、待补证、已关闭、重复处理。
- [x] 增加前置电销任务类型，和现有“退回事实核验”任务严格区分。
- [x] 定义每个状态的责任人、可执行动作、必填理由、所需证据、超时规则和可达下一状态。
- [x] 建立“电销提交事实结论 → 运营决定业务处置”的强制边界。
- [x] 所有电销任务均由运营管理员指定派发或改派；电销不得自主领取、转派或从公共队列取任务。
- [x] 任何状态变化都追加业务事件、审计日志、通知任务和时间线节点。

设计落实：列表状态同时显示“状态 + 当前责任人 + 下一步”；详情页始终展示来源、期限和全流程入口，禁止直接展示技术枚举。

验收：状态机负例测试覆盖越权、跳级、重复提交、过期任务和并发处理；电销 API 无法执行派发、关闭、退回加盟商或积分动作。

本轮验收记录（2026-08-25）：前置核验与退回核验均使用独立任务类型和配置化时限；超时任务会隐藏明文电话、拒绝开始/拨号/提交，并由运营改派后重新起算。改派审计在同一事务锁内保存责任人、期限、状态和版本的前后快照。

### 阶段 4：加盟商供资与前置核验闭环

- [x] 加盟商负责人/员工可创建和提交供资草稿；员工的数据范围限于本人草稿和被退回补正的记录。
- [x] 运营初审必须给出：合格、资料不全、重复、明确无效四类结论。
- [x] “资料不全”创建前置电销任务，由运营指定电销人员；电销只能接收被派发的任务。
- [x] 电销可提交真实、信息不全、无法核验、无效/重复等事实结论和依据。
- [x] 电销结论回到运营待办；运营决定入池、退回原加盟商补正、重复处理、关闭或再次核验。
- [x] 被退回供资必须保留原提交版本、退回理由、核验结论与重新提交历史。

设计落实：运营 H5/桌面“首页待办”首屏展示待初审、待核验结论和待处置；加盟商“供资”只显示本公司相关进度与补正原因。

验收：完整供资、资料不全、电话核验合格、电话核验不合格、补正后再提交、重复处理六条路径均可从录入走到终态。

本轮验收记录（2026-08-25）：运营初审收敛为四个受控结论；“资料不全”在同一事务中记录初审结论并创建指定电销的前置核验任务。加盟商端可见电话核验、运营处置和补正状态；初次提交、初审及运营处置审计均保存业务快照，补正后可回溯原提交内容、理由与再次提交记录，并重新向运营和加盟商投递本轮通知。运营 H5 首页待办将在阶段 8 统一补齐。

### 阶段 5：平台来源客资录入与处置

- [x] 运营管理员在“客资”中录入、编辑和提交平台来源客资。
- [x] 平台来源资料完整时，经运营确认进入待派发池。
- [x] 信息不全时进入前置电销核验，结论回运营。
- [x] 平台来源不合格仅允许补充、重复处理或关闭；不得错误显示“退回加盟商”。
- [x] 平台来源和加盟商来源在列表、详情、时间线和通知中清晰区分。

设计落实：运营“客资”页用来源筛选与状态队列组织内容；首屏只显示可处理队列，不把历史报表混入处理页。

验收：两个来源共享派发/领取规则，但上游补正责任和可操作按钮严格不同。

本轮验收记录（2026-08-25）：平台客资已迁入统一运营台，旧独立页面已删除并保留 302 兼容跳转。运营按来源筛选后，可保存平台草稿、资料完整直接入待派发池，或在有联系电话的前提下指定电销核验；电销提交事实结论后，由运营决定补充、重复、关闭或入池。平台来源的界面文案、通知场景和业务时间线均明确其补正责任属于运营，不显示“退回加盟商”。

### 阶段 6：加盟商审核、派发、领取与员工协作

- [x] 运营审核公司资料、供接能力和服务区域；支持一次操作通过同一申请中的能力与区域。
- [x] 审核结果同步影响派发候选资格，并向负责人发送通知。
- [x] 运营仅从待派发池人工派发，派发前校验公司启用、能力、区域、重复和积分可用余额。
- [x] 加盟商负责人领取时扣除积分，生成不可变流水。
- [x] 建立负责人将已领取客资分配给员工的关系、交接记录和可见范围。
- [x] 负责人在本公司内部直接分配或回收已领取客资，无需运营可见或审批；系统仅保留公司内部审计和交接记录。
- [x] 员工只查看自身任务；负责人可查看公司进度；运营仅查看公司级状态、数量和异常汇总，不得查看员工之间的分配明细；超级管理员按理由可审计查询内部记录。

设计落实：运营底栏/菜单的“派发”只放待派发池和候选判断；负责人 H5 的“接收”只放领取与员工分配；员工首页不显示公司级接收入口。

验收：停用、无能力、超区域、积分不足或重复的公司无法被派发/领取；员工无法访问未分配客户。

本轮验收记录（2026-08-25）：运营台已接入按公司“一键审核”，同一待开通申请中的能力和服务区域在一个事务内通过，待移除区域仍须单独审核。派发候选和领取继续在服务端校验公司启用、能力、区域、重复及可用积分；领取扣分和流水保持幂等。负责人 H5 可在本公司直接分配或收回已领取客资，系统保存业务事件与审计，员工仅能读取本人任务，运营只保留公司汇总，超级管理员必须填理由才能查内部明细。公司资料审核会生成站内消息与 Outbox；真实微信公众号发送仍需为 `V12_COMPANY_PROFILE_APPROVED`、`V12_COMPANY_PROFILE_REJECTED` 配置已审核模板并完成真实负责人微信 UAT。

### 阶段 7：跟进、退回、事实核验与运营终审

- [x] 跟进成功后关闭成交；“无效”不再只是跟进标签，必须进入正式退回或运营关闭流程。
- [x] 加盟商负责人/员工提交退回原因、事实说明和至少一种有效证据。
- [x] 系统创建退回事实核验任务；电销提交结论与通话依据。
- [x] 运营终审只能在电销结论存在时执行：通过、驳回、要求补证。
- [x] 通过时退还领取积分、取消/冲正供资奖励、解除原领取关系并回待派发池。
- [x] 驳回时恢复原加盟商跟进；要求补证时保留原证据并回到原申请人。
- [x] 再派发默认排除原领取公司，例外必须记录原因。

设计落实：负责人“跟进”内进入退回；员工从任务详情补证；运营“异常”页同屏展示申诉、证据、电销结论、截止时间、资金影响和终审动作。

验收：退回通过、驳回、补证、超时、重复提交、再派发六类场景均有正确积分、奖励、状态、通知和审计结果。

本轮验收记录（2026-08-25）：无效跟进会被服务端拒绝并引导为正式退回；负责人和员工必须附截图或录音后才能提交。退回核验只由运营派发给电销，电销仅提交事实结论和通话依据；运营在结论存在前不能终审。通过时返还积分、取消或冲正奖励并回待派发池；驳回恢复原跟进；要求补证保留原证据、回到原申请人并单独通知。退回后候选列表默认排除原领取公司；如确有必要再次派发，运营必须在服务端请求中显式填写例外原因，业务事件和审计同时记录。真实 COS 证据读写、微信模板消息和五角色 UAT 仍是上线前外部验收项。

### 阶段 8：积分、充值、奖励与财务治理

- [ ] 将原财务角色的充值、调账、套餐、价格、奖励、冲正功能迁入超级管理员的“资金”页面。
- [ ] 运营只见派发可用性和业务异常，不执行资金写入。
- [ ] 超级管理员的每笔资金操作必须填写原因、关联公司、金额/积分及凭证说明。
- [ ] 超级管理员资金操作不要求第二位超级管理员复核；仍必须受权限、审计、不可变流水和异常告警约束。
- [ ] 积分账户、占用、领取扣减、退回退款、奖励结算和冲正只以不可变流水为事实来源。
- [ ] 建立余额与流水对账，以及异常差异告警。

设计落实：超级管理员 H5/桌面“资金”先展示对账异常、冻结奖励和待审批事项，再展示操作表单；加盟商“我的”只读显示积分、奖励和充值联系入口。

验收：运营和电销无法调用任何资金写接口；任一余额变化均能追到操作人、业务单据、前后余额和审计记录。

### 阶段 9：五角色 H5 工作台重设计

- [ ] 实现五套首页待办模块与角色化 KPI，不复用无关模块或数据。
- [ ] 新增 `/h5/admin/` 响应式平台移动工作台；以单一 V1.2 壳按角色渲染超级管理员与运营管理员页面，不复制旧后台。
- [ ] 超级管理员移动端实现：首页（待办/风险）→ 治理（账号公司事项）→ 资金（充值、调整、冲正、异常）→ 我的；复杂批量治理、长审计导出留在桌面端。
- [ ] 运营移动端实现：首页（待办）→ 客资（初审、前置电销、运营处置）→ 派发（单条派发确认）→ 异常（退回、逾期、公司异常）→ 我的；批量操作留在桌面端。
- [ ] 电销 `/h5/call/` 完善为：首页（待办）→ 核验（本人任务与拨号）→ 记录（已提交及运营处理结果）→ 我的；同时保持桌面响应式可用。

- [ ] 固化五套两字底栏：
  - [ ] 超级管理员：首页、治理、资金、我的；
  - [ ] 运营管理员：首页、客资、派发、异常、我的；
  - [ ] 电销人员：首页、核验、记录、我的；
  - [ ] 加盟商负责人：首页、接收、供资、跟进、我的；
  - [ ] 加盟商员工：首页、跟进、供资、我的。
- [ ] 所有首页的第一个模块为“待办”，按 SLA、状态和责任人排序；无待办时展示角色相关空态和唯一主操作。
- [ ] 消息不占用底栏，仅在相关任务或“我的”显示有行动价值的未读提醒。

设计落实：沿用现有暖色 Token、SVG 图标和底部导航组件，不引入第二套设计系统；H5 页面不显示原始状态码、权限码、财务敏感信息或旧页面入口。

验收：390×844 真机/浏览器视口下无横向溢出；五角色登录后只出现其设计的底栏与工作流，且任一指标卡都能进入对应待办。

## 4. 实施顺序与提交原则

1. 阶段 1–3 先完成：不稳定的角色和状态机不能直接套新页面。
2. 阶段 4–8 按业务链路完成并各自独立测试。
3. 阶段 9 与阶段 10 在后端合同冻结后实施，避免页面反复重写。
4. 每阶段独立提交、独立验收、可 `git revert`；不将角色迁移、数据迁移和页面删除混在同一提交。
5. 实施期间禁止新增旧版页面入口；任何发现的旧页依赖都记录为迁移任务，不临时回跳解决。

## 5. 已确认的业务决定

- 加盟商员工和加盟商负责人都可以直接提交客资；员工仅处理本人创建或负责人分配的供资记录。
- 加盟商负责人可直接在本公司内分配、回收已领取客资，无需运营可见或审批；保留公司内部操作记录。
- 运营仅查看加盟商公司的状态、数量和异常汇总，不查看员工之间的分配明细；超级管理员需填写理由后才可审计查询该内部记录。
- 超级管理员可直接完成任意金额/积分的资金操作，无需第二位超级管理员复核；每次操作仍需原因、凭证说明、不可变流水和审计。
- 超级管理员与运营管理员均可开通、启用、停用和绑定加盟商负责人/员工账号；超级管理员的该类操作必须保留理由、前后状态和高风险审计。
- 电销任务仅允许运营管理员派发或改派；电销不得自主领取、转派或决定后续业务处置。
- 电销工作台必须同时提供移动端和桌面端；移动端采用用户点击后调起系统拨号盘的方式，不能网页静默自动外呼。

上述决定和 `DESIGN.md` 共同构成本轮实施合同。
