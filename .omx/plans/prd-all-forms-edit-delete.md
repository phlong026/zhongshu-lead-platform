# PRD：全系统表单编辑、安全删除与状态化更正

状态：已批准
日期：2026-08-24
关联方案：`.omx/plans/ralplan-all-forms-edit-delete.md`

## 1. 目标

为生产 V1.2 管理端、加盟商 H5、供客 H5、电销 H5 中会产生持久化记录的表单补齐可搜索、可编辑以及可解释的删除替代动作，同时不破坏派发、积分、奖励、审核和审计链路。

首要结果：

1. 人工派发可按公司名称搜索并选择候选公司。
2. 人工充值可搜索加盟商公司，可选固定积分档或输入自定义积分。
3. 加盟商已保存的基础资料可编辑、停用和恢复。
4. 其余持久化表单按状态提供编辑、软删除、撤回、归档、释放、作废、关闭、冲正或只读动作。

## 2. 产品规则

### 2.1 统一交互，分层语义

列表和详情统一展示“编辑”和“删除或撤销”动作入口，但最终动作由对象状态决定：

| 对象状态/类型 | 编辑动作 | 删除替代动作 |
|---|---|---|
| 未提交草稿 | 直接编辑 | 软删除到回收站，30 天内恢复 |
| 待审/待激活 | 撤回后编辑再提交 | 撤回或平台驳回 |
| 公司等主数据 | 编辑基础资料 | 停用 `DISABLED`；允许恢复 `ACTIVE` |
| 已发布配置 | 复制为新草稿 | 过期或 `RETIRED` |
| 待领取派发单 | 核心字段只读 | release 回派发池 |
| 已领取/跟进/完成事实 | 追加更正 | 关闭、退回或作废，不删除原记录 |
| 积分/奖励流水 | 不编辑 | 冲正，原流水永久保留 |
| 审计、轨迹、通知 | 只读 | 不提供删除 |

高风险动作必须具备后端权限校验、原因、二次确认和 before/after 审计。前端隐藏按钮不作为安全边界。

### 2.2 服务资格

公司名称、负责人、电话、备注属于基础资料，可直接编辑。服务区域以及供客/接客能力属于资格配置，任何增加、删除或修改均提交审核；批准前当前已生效配置继续参与派发资格。

### 2.3 数据保留

- 草稿软删除后进入 30 天回收站；普通列表默认隐藏。
- 回收站支持恢复；到期清理通过默认 dry-run 的运维任务执行。
- 有派发、退回、积分、奖励或其他下游引用的记录不得物理删除。
- 文件证据作废后仍保留对象 key、哈希和原始元数据。

## 3. P0 用户故事

### 3.1 人工派发

作为运营人员，我可以在候选公司弹窗按公司名称过滤，以快速找到目标公司；候选资格、积分、服务区匹配和不可派原因仍由后端计算。

验收：

- 搜索只过滤当前后端返回的候选列表，不改变候选来源、排序来源或资格判断。
- 清空搜索恢复全部候选；无结果时给出明确空状态。
- 不恢复、不增强 legacy 派发 mutation。
- 只有 `PENDING_CLAIM` assignment 可 release；其他现有状态返回 409。

### 3.2 人工充值

作为财务人员，我可以搜索加盟商公司，选择固定充值档，或输入自定义积分和实际线下收款金额。

验收：

- `package_id` 与 `custom_points` 必须且只能提供一个。
- 自定义积分为正整数，线下实收为正数。
- 自定义充值写 `RECHARGE` 流水，不改变公司等级或套餐权益。
- 相同幂等 key 只有请求指纹完全一致才返回原结果，否则 409。
- 非空付款流水号全局唯一；换 key 重放同一流水号仍返回 409。
- 成功后保留通知、Outbox 与审计。

### 3.3 加盟商公司

作为运营人员，我可以编辑公司基础资料；我可以停用和恢复公司，但不能物理删除已被业务引用的公司。

验收：

- 名称、负责人、电话、备注可编辑。
- 脱敏手机号不能作为完整手机号写回。
- 停用使用 `DISABLED`，恢复使用 `ACTIVE`。
- 服务区/能力不允许通过基础资料接口直接替换。

## 4. P1 用户故事

### 4.1 客资草稿和退回申请

- 平台与供应商草稿可编辑、软删除、在 30 天内恢复。
- 待审内容先撤回再编辑；已派发或已审结内容不删除。
- purge 仅处理无下游引用的到期草稿，并输出候选、跳过原因和操作审计。

### 4.2 跟进记录

- 跟进记录不可原地改写。
- 用户通过“作废并更正”保留原记录并追加替代记录。
- 当前跟进状态按最新有效记录重算；作废成交记录后必须恢复到最新有效非成交状态。

### 4.3 退回证据

- 文件不可原地替换，用户可上传新证据并作废旧证据。
- 证据汇总和提交校验仅统计未作废证据。
- 作废后证据不足时，退回申请回到补证或禁止提交。

### 4.4 配置与规则

- 草稿可编辑、删除、恢复。
- 已发布配置不可原地编辑；“编辑”复制为新草稿。
- 积分档位和价格规则沿用 `effective_at/expires_at/status`。
- 系统配置和奖励规则沿用 `version/status/effective_at/published_by`，旧版以 `RETIRED` 退场。

## 5. P2 范围

- 电销核验任务支持领取前 release/cancel/reassign；提交后只追加复核。
- 审计、派发事件、通知只读，增加筛选和导出而非编辑删除。
- 按业务需要补充操作手册与指标面板。

## 6. 权限与审计

需要新增或确认：

- `assignment.release`
- `company.update`
- `company.disable`
- `company.restore`
- `lead.restore`
- `lead.purge`
- `return.evidence.void`
- `followup.void`
- `config.version.manage`

每个动作记录 actor、resource、before/after、reason、request_id、IP 和 user agent。权限矩阵、同步脚本与 exact-sync 测试必须同步更新。

## 7. 非目标

- 登录、查询筛选、确认弹窗和只读详情不纳入“所有表单”。
- 不在 P0/P1 引入通用 event sourcing。
- 不修改历史积分/奖励流水，不级联删除业务链。
- 不恢复 legacy 派发接口。

## 8. 分期与完成定义

1. Phase 0：锁定现有关键行为与 legacy 边界。
2. Phase 1：派发搜索/release、充值搜索/自定义、公司基础资料编辑与停用恢复。
3. Phase 2：草稿回收站、恢复、purge dry-run/apply。
4. Phase 3：跟进更正、证据作废、状态投影重算。
5. Phase 4：配置版本化和 retire。

每一期只有在目标行为测试、越权测试、迁移检查、静态检查和相关端到端验收通过后才算完成。
